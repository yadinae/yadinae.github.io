我让 AI Agent 从自己的失败中学习——失败模式自动挖掘 + 规则生成实战

发表于2026-08-29|更新于2026-09-02|技术实践

59 个失败模式、42 条机器可读规则——全部由 Agent 从自己的会话历史中自动挖掘生成。这篇记录我怎么让 AI Agent 学会「从自己的错误中学习」，把「改了 A 忘了 B」这类集成 bug 变成可自动检测的规则。

1. 缘起：同样的坑，踩了三次

事情要从 Cloudflare Workers 项目说起。

我有一个网盘应用（TG Cloud Drive），前端在 Cloudflare Pages，后端是 Workers。每次部署新功能，我都会遇到同一类 bug：

  • 第一次：前端加了 X-Session-Id 请求头，CORS 没配 → 跨域报错
  • 第二次：登录改用 session 后，文件移动功能还在读旧的 localStorage → 移动失败
  • 第三次：新加了 GET 接口没写 Cache-Control → 用户看到旧数据

三次，三种表现，同一个根因：改了 A 但忘了 B。

我意识到这不是偶然——这是所有前后端分离项目的通病。而我的 AI Agent 每天都在帮用户部署代码，它也应该能从这些失败中学习。

于是我想：能不能让 Agent 自动挖掘自己的失败历史，把「踩过的坑」变成「可自动检测的规则」？

2. 核心方法：三层防线 + 反馈闭环

2.1 三层防线架构

核心思想：失败不是 bug，而是训练数据。

每一次部署失败，都是一个可以被系统化捕获的模式。捕获后，它不再是「下次注意」，而是一条可以被脚本自动检测的规则。

2.2 自动挖掘：从会话历史中提取失败模式

这是最有意思的部分。我写了一个 auto_discover_patterns.py，它会：

  1. 扫描最近 48 小时的会话历史（从 Hermes 的 state.db 中读取）
  2. 用关键词匹配用户报告的失败（”failed”、”失效”、”报错”、”CORS” 等）
  3. 用分类器判断失败类型（CORS / Auth / Cache / Route / KV）
  4. 去重（用 n-gram 相似度判断是否已有类似模式）
  5. 自动生成模式条目写入 failure-patterns.json

关键设计决策：

  • 用用户原话而非 Agent 总结：用户说”CORS 报错”比 Agent 说”跨域配置问题”更精准，因为用户描述的是症状，症状才是检测的入口
  • 上下文窗口策略：匹配到失败关键词后，往前看 5 条消息获取上下文，用于提取修复方案
  • n-gram 去重：用 8-gram 相似度判断重复，比简单字符串匹配更抗改写

这个转换不是简单的格式变换——它需要从自然语言描述中提取结构化信息：

  • CORS 模式 → 提取 header 名称

  • Cache 模式 → 提取 endpoint 路径
  • Route 模式 → 提取 fetch 路径

提取失败时，用合理的默认值兜底（比如 CORS 默认检查 X-Session-Id），宁可误报也不要漏报。

  • 路由不匹配：前端 fetch 路径没有对应的后端路由

  • KV/D1 Schema 漂移：旧的 key 前缀仍在使用

3. 实战数据：59 个模式从哪来

运行两周后，系统自动挖掘出了 59 个失败模式，分布如下：

类型 数量 典型场景
Cache 21 GET 接口缺 Cache-Control，用户看到旧数据
Auth 15 登录改 session 后旧 localStorage key 仍在用
Route 14 前端 fetch 路径变了但后端路由没跟上
CORS 5 新请求头没加到 allowHeaders
KV 4 数据库 key 前缀迁移后旧引用残留

100% 由 detected_by: auto 标记——没有一条是我手动录入的。

最有价值的发现：21 个 Cache 模式中，有 12 个是「看起来修好了但其实没修好」的变体。比如：

  • 修了 /api/shares 但忘了 /api/shares/list
  • 加了 Cache-Control 但没加 no-store
  • 主路由加了但子路由没加

这些细微变体，靠人工记忆几乎不可能全覆盖，但脚本可以。

4. 踩坑记录

4.1 分类器的精度问题

最初的设计是「所有包含 failure 关键词的消息都算失败」，结果误报率极高：

  • “这个功能不支持” → 不是失败，是能力边界
  • “检查下有没有报错” → 不是失败，是预防性询问
  • “失败模式自动挖掘” → 不是失败，是功能名称

修复：加了排除规则——包含 “IMPORTANT”、”context compaction” 的消息直接跳过，消息长度 < 10 字符的跳过。更精细的排除需要 LLM 理解，但那就不是”自动挖掘”了。

4.2 去重的挑战

同一类 bug 会以不同表述反复出现：

  • “CORS 报错了”
  • “跨域请求被拦截”
  • “access-control-allow-headers 缺少 X-Session-Id”

简单的字符串匹配无法识别这些是同一个问题。最终用 8-gram 相似度——把文本切成 8 字符的片段，计算集合重叠度。对中文（5 字一个词）和英文（常见单词 4-6 字符）都能工作。

4.3 规则膨胀

59 个模式中有不少是「同义反复」——同一类问题的不同表述被当成不同模式。42 条规则中，实际有效的独立规则可能只有 15-20 条。

改进方向：在 update_skill_from_patterns.py 阶段增加聚类，把相似规则合并。目前靠 rule_exists() 的结构化字段匹配来抑制膨胀，但对「同一 header 的不同表述」仍然无能为力。

4.4 规则的保质期

有些规则是临时的——比如某个 API 正在迁移期间的检查项，迁移完成后就成了噪声。

解决思路：给规则加 expires_at 字段，超过有效期自动降级为「参考」而非「阻断」。目前还没实现，但已经在 roadmap 上了。

5. 总结

核心洞察：Agent 的失败历史是最宝贵的训练数据——不是用来微调模型的，而是用来生成可执行规则的。

行动建议：

  1. 记录每一次部署失败——不是写文档，而是结构化存储（类型 + 标题 + 描述 + 修复方案）
  2. 定期扫描会话历史——用关键词 + 分类器自动发现新模式
  3. 把模式转成规则——从自然语言描述中提取结构化检测项
  4. 在部署前自动扫描——verify.py 式的 pre-flight check，exit code 集成 CI

代码仓库：所有脚本位于 ~/.hermes/skills/software-development/pre-deployment-verification/scripts/

一句话总结：不要让 Agent 「下次注意」——让它把失败变成规则，下次自动检查。

本文代码基于 Hermes Agent 的 pre-deployment-verification 技能，运行在日常 cron 任务中。59 个模式、42 条规则全部由系统自动生成，未做人工筛选。
