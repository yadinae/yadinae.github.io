4 个 AI Agent 接力写收盘报告——Kanban 多 Profile 流水线实战

发表于2026-08-26|更新于2026-09-11|技术实践

一个 Cron 任务不自己干活，而是创建 4 个 Kanban 任务、分配给 3 个不同的 AI Profile、按依赖链自动流转——research 并行抓数据、critic 交叉验证、writer 汇总出报告。这篇记录我怎么从「一个 Agent 做所有事」进化到「流水线编排」，以及为什么 Kanban 是 Agent 协作的隐藏利器。

1. 缘起：一个 Agent 的分析瓶颈

上一篇博文（《我用 6 个 AI Bot 搭了一个虚拟团队》）讲了怎么把一个万能 Bot 拆成 6 个专注 Profile。但拆完之后我很快发现一个新问题：

收盘分析这种多步骤任务，单个 Profile 仍然吃力。

每天 16:10 A 股收盘后，我需要：

  1. 拉大盘数据（上证/深证/创业板/北向资金/板块轮动）
  2. 诊断每只持仓ETF的技术指标（MACD/RSI/均线/资金流）
  3. 做风控研判（多空对比、止损提醒、仓位建议）
  4. 写成一份结构化报告发到飞书

一开始，这些全塞在一个 cron prompt 里。结果：

  • 上下文爆炸：一个 prompt 要塞持仓数据 + 大盘数据 + 技术指标 + 分析指令，token 消耗巨大
  • 质量不稳定：同一个 Agent 既抓数据又分析又写报告，容易「自说自话」
  • 无法并行：大盘分析和持仓诊断其实是独立的，但串行执行浪费时间

我需要的不是一个更强的 Agent，而是一条流水线。

2. 核心架构：Cron → Kanban → Profile

2.1 三层编排模型

关键设计：Cron 任务（Orchestrator）不自己执行分析，只负责创建 Kanban 任务并分配给对应的 Profile。每个 Profile 专注自己擅长的事。

2.2 四个任务的职责

任务 Profile 输入 输出 并行性
T1 大盘与板块分析 research 市场数据 API 指数涨跌 + 板块轮动 + 资金流向 与 T2 并行
T2 持仓诊断 research 持仓列表 + 行情 API 逐股技术指标 + 风险信号 与 T1 并行
T3 风控与多空研判 critic T1 + T2 的输出 多空对比 + 止损提醒 + 仓位建议 等 T1+T2
T4 综合报告 writer T3 的输出 飞书格式的最终报告 等 T3

2.3 为什么是 Kanban 而不是简单的串行调用？

方案 优点 缺点
单 Agent 全做 简单 上下文爆炸、质量不稳定
串行调用链 有先后顺序 无法并行、无任务状态
Kanban 流水线 并行 + 依赖 + 状态追踪 需要 Kanban 基础设施

Hermes 内置的 Kanban 系统天然支持：

  • 任务依赖：T3 自动等 T1+T2 完成后才启动
  • 并行执行：T1 和 T2 同时被 research profile 领取
  • 状态追踪：todo → ready → running → done，全流程可视
  • Profile 路由：每个任务指定 assignee，自动分发到对应 Profile

3. 实现细节

3.1 Orchestrator Prompt（Cron 任务的核心）

这是整个流水线的「大脑」。Cron 任务的 prompt 不是让 Agent 分析市场，而是让它创建 Kanban 任务：

核心思想：Orchestrator 的输出不是分析结论，而是任务创建指令。它在 2 分钟内完成所有任务创建，然后就退出了——真正的分析由各个 Profile 异步执行。

3.2 Profile 的专业化

每个 Profile 有自己专门的技能和工具集：

为什么这样分？ 因为「抓数据」和「做判断」和「写报告」是三种完全不同的能力。让一个 Agent 同时做三件事，就像让一个人同时当程序员、产品经理和设计师——每个都能做，但每个都做不好。

3.3 依赖链的自动流转

Hermus Kanban 的依赖机制：

  • T1 和 T2 创建后立即进入 ready 状态，research profile 可以同时领取
  • T3 创建时带 --parent T1 --parent T2，状态为 todo，等 T1 和 T2 都 done 后自动变 ready
  • T4 依赖 T3，同理

实测时间线：

总耗时 ~10 分钟，其中 T1+T2 并行节省了约 4 分钟。如果串行执行，至少需要 14 分钟。

4. 踩坑记录

坑 1：Orchestrator 误把自己当执行者

症状：Cron 任务 prompt 写的是「分析今日大盘走势」，结果 Orchestrator 自己调 MCP 拉数据做分析，创建的 Kanban 任务没人领。

原因：prompt 里同时有「分析」指令和「创建任务」指令，Agent 选择了更熟悉的「直接分析」。

修复：prompt 里加硬性规则——

坑 2：依赖链断裂——parent ID 传错

症状：T3 一直是 todo 状态，永远不启动。

原因：Orchestrator 把 T1 的任务标题当成了 task ID 传给 --parent。

修复：用 --json 参数获取真实 ID：

坑 3：Research Profile 同时领了两个任务但串行执行

症状：T1 和 T2 虽然都是 ready，但 research profile 一个做完才做另一个。

原因：Hermes 的 Kanban worker 默认单线程——一个 Profile 同一时间只处理一个任务。

修复：确认 research profile 的并发度设置为 2（concurrent_tasks: 2），或者接受串行（对分析质量影响不大，只是多几分钟）。

坑 4：Critic 没拿到 T1+T2 的完整输出

症状：T3 的风控研判缺少大盘数据，只看了持仓。

原因：Kanban 任务的 body 只传了指令，没传 T1+T2 的实际输出。

修复：在 T3 的 body 里加「读取 T1 和 T2 的任务输出」指令：

Profile 可以通过 Kanban API 读取 parent 任务的输出。

5. 这个模式能复用吗？

能。 Kanban 多 Profile 流水线不只适用于投资分析。任何多步骤、多角色、有依赖关系的任务都可以用这个模式：

场景 T1 T2 T3 T4
收盘分析 大盘数据 持仓诊断 风控研判 综合报告
代码评审 代码扫描 测试运行 安全审计 评审报告
内容生产 素材收集 框架提取 质量审核 文章发布
竞品分析 产品调研 用户评价 技术拆解 分析报告

核心原则：

  1. Orchestrator 不干活——只创建任务、分配角色、监控进度
  2. 独立任务并行——没有依赖关系的任务同时执行
  3. 有依赖的任务串行——通过 --parent 建立依赖链
  4. 每个 Profile 专注一件事——research 做调研、critic 做判断、writer 做输出

6. 总结

一句话 takeaway：当单个 Agent 做不好一件事时，不要优化 prompt——拆成多个 Agent，用 Kanban 编排。

从「一个 Agent 做所有事」到「Kanban 流水线」，我的 Agent 系统经历了一次架构升级：

v3 的核心收益：

  • ⚡ 速度提升 ~30%：T1+T2 并行节省 4 分钟
  • 🎯 质量提升：critic 交叉验证，避免「自己审自己」
  • 📊 可观测：Kanban 看板实时显示每个任务的状态
  • 🔄 可复用：同样的模式适用于代码评审、内容生产等场景

如果你也在用 AI Agent 做复杂任务，不妨试试「Orchestrator + Kanban + 多 Profile」这个组合。它比你想的更简单，效果也比你想的更好。
