技能库也会断链：我给 190 个互相引用的 AI 技能装了每日契约巡检

发表于2026-10-10|更新于2026-10-10|AI 工程实践

一句话摘要：技能越剪越少，引用越断越多。一篇 50 天、1157 条发现的巡检实录，讲清楚”技能路由契约”到底是什么、怎么把 154 个误报压到 7 个，以及为什么这类扫描器必须只报告、不拦截。

1. 缘起 — 剪枝的爽感，和引用的暗伤

我的 Hermes 技能库在 9 月中到 10 月初经历两轮大瘦身：峰值 255 个活跃技能（09-02），到 10-09 只剩 190 个。剪完之后目录清爽、description 列表变短、agent 选技能时不再被无关项干扰——那种爽感和把衣柜清空一模一样。

但两周后我注意到一件不对劲的事：有几次 agent 按 SKILL.md 里的指引去”用某某技能”，加载失败了。翻回去看，那个技能早就被我挪进 .archive/ 了，而引用它的文档纹丝不动。

这暴露了一个结构性问题：Hermes 没有中心路由。技能不是靠斜杠命令注册的，是 agent 读 description 自主 skill_view(name=...) 加载的。于是技能之间的互相引用——“用 X 技能”、”详见 Y”、skill_view(name='z')——变成了一份口头契约：没有任何机制保证它有效，技能被改名、归档、删除时不会有任何东西报错，直到某天 agent 按图索骥踩空。

更隐蔽的是：剪枝动作本身就是断链的主要来源。你删的每一个技能，都可能是别人文档里的”下一步”。

于是有了这个每天中午 12:30 跑一次的巡检。先放结论性的数字：

  • 扫描器：check_skill_routing_contract.py，474 行，08-05 上线
  • 累计执行 66 次，留存 50 份巡检记录
  • 50 天累计报告 225 条 ERROR + 932 条 WARN = 1157 条发现
  • 0 次全绿（这也是后面要讲的重点）

2. 核心方法

2.1 先想清楚：你的系统里”契约”到底长什么样

灵感来自 dontbesilent2025/dbskill（9.2k stars）里的 check-skill-routing-contract.py：它强制”所有叶子技能必须交回 /dbs 路由器”，靠 Claude Code 的插件市场 CI 正则门禁来执行。

照抄行不行？不行。dbskill 的契约能成立，是因为它有中心路由 + CI 门禁两个前提；Hermes 两个都没有——没有 /dbs 这种东西，也没有 repo 级 CI 会拦截一次 push。如果你照抄，得到的是一份纸面契约：规则写着，没有任何东西执行它，你还得为它发明一个假路由器。

所以第一步是改契约本身：

Hermes 的可执行契约 = 引用有效性（被引用的技能还存在吗？），而不是”交回路由器”。

顺带一提，dbskill 是 CC BY-NC 4.0，代码不能直接搬——所以最终是借设计、重写实现（474 行从零写，只保留 verdict 分类思想）。

原则一：契约不是设计出来的，是被你的架构约束出来的。 照抄别人的 CI 契约之前，先问你的系统里谁来执行它。

2.2 分类学先行：先定义 verdict，再写正则

扫描器的核心不是正则，是一张判定表。每一条疑似引用最终落到一个 verdict：

verdict 含义 动作
error 引用了不存在的技能 断链：修引用或装技能
warn 引用了 .archive 里的技能 看语境：指令性引用要改，历史提及可忽略
external 合法的库外依赖（~/.claude/skills/*、上游仓库） 记录，不修
directive 硬编码路由到一个存在的技能 只计数
ok 引用有效 通过
placeholder / noise 模板词、目录名、概念词 过滤掉

这里有个容易做错的判断：directive（”下一步用 X 技能”这种硬路由）在 dbskill 里是违规，在 Hermes 里却只计数不判错——因为 Hermes 本来就允许技能间互相衔接，真正违规的只有”衔接到了不存在的东西”。

原则二：先定义判定分类，再写匹配规则。 正则只是把可疑行捞出来的渔网，verdict 才是让人能一眼决定”修 / 忽略 / 记录”的那一步。

2.3 信噪比之战：154 个误报 vs 13 个真问题

第一版扫描跑出来的结果是：约 154 个误报 / 13 个真问题。信噪比差到没人愿意看——于是后面大半的工作量都花在压误报上，一共沉淀了九类过滤器：

  1. PLACEHOLDER_TOKENS — 写文档时的模板词：your-skill、another-skill、skill-name-here
  2. CONCEPT_SKILL_TOKENS — 描述”写技能 / 加载技能”这类活动的词：writing-skill、skill-loading，以及 code-review 这种纯概念
  3. EXTERNAL_SKILL_TOKENS — 库外合法依赖：~/.claude/skills/ 下的技能、上游 GitHub 项目、表格里举例的技能
  4. NOISE_TOKENS — 技能内部目录名：references、templates、scripts
  5. CATEGORY_NAMES — 顶级分类目录名（devops、research），它们可能和某个归档技能同名
  6. 文件后缀守卫 — “见 xxx.py“ 是文件引用，不是技能引用
  7. 正则 lookahead — (?![\w-])，防止 darwin-skill 命中 darwin-skill-optimizer
  8. TOOLSET_TOKENS — Hermes 内置工具集名（spotify、discord、feishu_doc），恰好和归档技能重名
  9. is_documentary_context() — 行内出现 formerly / ported from / 示例 / e.g. / 历史记录 的，判定降级为 info

第 9 条是被现实逼出来的：巡检脚本自己的基线文档里就写着”某某技能已归档”，不降级的话，扫描器会每天报告自己文档里的历史记录是断链（自引用噪声）。所以这条规则必须在 descriptive 和 backtick 两个分支都生效——只加一个分支，另一半噪声照样刷屏。

两份契约叠在一起：

  • 静默契约：全绿 → 空 stdout → cron 不投递 → 你一条消息都收不到；有发现 → markdown 简报原样推飞书
  • 基线契约：退出码恒为 0（脚本注释写明”后续接入门禁可改 --gate“，但门禁没启用）——只报告，不拦截

为什么不拦截？看下一节的数据。

3. 50 天数据 — 归档动作制造断链

日期 活跃技能 ERROR WARN 事件
08-20 234 2 0 巡检上线初期
09-02 255 2 0 技能数峰值
09-04 243 2 18 出现首批归档引用
09-18 205 3 29 批量归档 −45，WARN +9
09-25 203 8 23 ERROR 达峰
10-02 191 7 39 批量归档，WARN +16
10-09 190 7 39 最近一次巡检

三个发现：

① 归档动作直接制造断链。 两次批量归档分别让 WARN 从 20→29（+9）和 23→39（+16），同时告警的技能名单整体换血——google-workspace、notion 这些引用消失了，test-driven-development、adversarial-solver 这些新归档的技能顶了上来。引用断不断，完全跟着你剪刀的动作走。

② 50 天 0 次全绿。 225 条 ERROR 拆开看只有 7 类词：add-skill（62 次）、security-audit-skill（58 次）、other-in-repo-skill（42 次）、critic（28 次）、judge（15 次）、fusion（15 次）、opencode-go（5 次）。逐条人工裁决后全部是词法误报：

  • add-skill 是 CLI 参数 hermes cron edit <id> --add-skill <name>，不是技能
  • security-audit-skill 是磁盘上真实存在的输出目录 ~/security-audit-skill/，只是不在技能库里
  • critic 来自”critic 路由且未超预算”（模型路由），judge 来自”交给 judge 模型重写”，fusion 来自”跟主力切到 fusion”——中文指令动词 + 英文普通词，恰好命中 DIRECTIVE_PATTERNS

③ 真正的信号在 WARN 里。 39 处归档引用里，systematic-debugging 写着”Use the test-driven-development skill”——而那个技能已经躺在 .archive/ 里了。这是货真价实的失效指令，agent 照做就会加载失败。

结论：这就是”只报告不拦截”的理由。 假如启用了 --gate 让它在 CI 里挡路，你第二天就会面对两个选择：要么为了通过门禁去”修”一堆根本没坏的东西，要么直接把扫描器关掉。基线模式让人做裁决、让误报有机会回灌进过滤器——扫描器的价值不在于它红了多少次，而在于它红的原因被人分类过多少次。

坦白说，目前还有欠账：那 7 类误报已经被反复投喂了 50 天，却还没被加进 PLACEHOLDER_TOKENS / NOISE_TOKENS。裁决结果必须回灌，否则告警永远是红的，红色就再也没有意义了。这是接下来要做的第一件事。

4. 踩坑记录

坑 1：归档脚本的 dirname 差一层，7 个分类目录被整锅端。 算技能根目录时 os.path.dirname(f) 是对的，os.path.dirname(os.path.dirname(f)) 就变成了分类目录——2026-08-02 真实事故：creative / devops / mlops / gaming / research / smart-home / software-development 七个分类连同下面所有兄弟技能一起被搬进了归档，事后靠逐个校验 SKILL.md 才恢复。规则：只移动”直接包含 SKILL.md 的目录”，移动前先 os.path.exists(target/SKILL.md)。

坑 2：技能有三层深度，一个 find 模式必然漏。 顶级 <skills>/<name>/、分类 <skills>/<category>/<name>/、嵌套 <skills>/<category>/<sub>/<name>/（如 mlops/cloud/modal/）。批量操作必须递归枚举所有含 SKILL.md 的目录。

坑 3：read_file 把中文 SKILL.md 判成二进制。 返回”Binary file - cannot display as text”，而 file 明明说是 UTF-8 纯文本。绕过办法：python3 -c "import io; print(io.open(path, encoding='utf-8').read())"。

坑 4：文件 atime 完全不可信。 relatime 挂载下统计出来 232/232 技能全部”最近访问”，按 atime 判断活跃度等于全绿。真正的使用数据在 ~/.hermes/state.db 的 messages.tool_calls 里数 skill_view 调用。

坑 5：0 次调用 ≠ 0 使用。 cron 任务按技能名直接加载，不走 skill_view——activeagent-optimizer 这类技能调用次数为 0 却天天在用。归档前必须交叉 jobs.json 的 skill/skills 字段。

边界：什么时候不需要它。 技能少于几十个、彼此不交叉引用 → 人眼可及；系统本身有中心路由和 CI → 直接用 dbskill 原版的”交回路由”契约更强。它适用的场景只有一个：多、散、互相引用、没有中心调度的技能库。

5. 总结

  • 核心结论：契约的形态由架构决定。没有中心路由的系统，别签”交回路由器”的约，签”引用有效”的约——一份能被执行的弱契约，胜过一份没人执行的强契约。
  • 一条铁律：扫描器只报告、不拦截；每次人工裁决的结论（真问题去修、误报进过滤器）必须当天回灌，否则红色会通胀成背景噪声。
  • 一句话 takeaway：技能库的腐化不是发生在你删技能那一刻，而是发生在别人还没更新的那份文档里——所以巡检的应该是引用，不是技能本身。
