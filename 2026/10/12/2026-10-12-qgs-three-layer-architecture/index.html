QGS 三层架构：把质量门禁变成可组合的基础设施

发表于2026-10-12|更新于2026-10-21|技术架构

传统的 LLM 质量评审是黑盒：全靠一个大模型输出 JSON，既定位不准、又高误报、还贵。QGS 三层架构把判断拆成 确定性快筛（Layer1）+ 语义判断（Layer2）+ 独立反思（Layer3），把质量门禁从”评分器”变成了可组合、可调试、可扩展的基础设施。

1. 缘起 — 为什么要重构 QGS

1.1 痛点：纯 LLM 评审的三大顽疾

最早的 QGS（Quality Gate System）是个纯 LLM 评审器：把交付物塞进 prompt，让模型打分、给建议、输出 JSON。跑了一段时间后，三个问题暴露无遗：

问题 表现 后果
位置不准 LLM 只能”猜”行号，经常指错文件、错行、甚至幻觉出不存在的函数 开发者无法定位修复，信任度归零
误报率高 同一段代码，换个温度、换个模型，结论可能反转；测试文件里的 print() 也被当 P2 报上来 噪音淹没信号，评审变成”狼来了”
成本失控 每次评审都要调一次大模型，Token 消耗不可控；想加规则只能改 prompt，版本管理混乱 规模上不去，迭代慢

4. 踩坑记录 — 反例与边界

4.1 坑 1：规则正则的贪婪匹配

早期 hardcoded-url 规则用 (?i)(https?://|http://)\S+，把 markdown 里的链接、日志里的 URL 全报了。

修复：细化排除路径 + 上下文感知：

4.2 坑 2：Layer 1 扫不到动态生成的代码

交付物里包含字符串拼接的 SQL、模板渲染后的代码，Layer 1 扫的是源文件，漏报。

缓解：Layer 2 prompt 里强制要求”检查交付物中嵌入的代码片段”，Layer 3 反思专门查”动态生成内容”。

4.3 坑 3：反思模块偶尔”为了反思而反思”

Layer 3 偶尔会强行找问题，把原本正确的 dismissed_as_false_positive 判成 missed_issues。

缓解：

  • 调低 temperature=0.3，加 response_format={"type": "json_object"}
  • 在 merge_reflection 里做二次校验：只合并 severity ≥ P2 的遗漏问题
  • 加人工复核入口：QGS_REFLECTION_HUMAN_REVIEW=1 时落盘供人工确认

4.4 坑 4：环境变量控制不够细粒度

最初只有 QGS_LAYER1=1 / QGS_REFLECTION=1 两个开关，想”只跑 Layer1 不跨 Layer2”做不到。

5. 复用场景 — 不止于内容生成

三层架构的核心模式 确定性快筛 → LLM 慢审 → 独立复核 可迁移到任何需要”质量门禁”的场景：

场景 Layer 1 规则示例 Layer 2 语义判断 Layer 3 反思焦点
代码审查 语法错误、禁用 API、安全模式 架构一致性、设计模式滥用、性能隐患 遗漏的安全洞、过度设计
数据校验 Schema 合规、非空、枚举值 业务逻辑自洽（如：订单金额=明细求和） 异常分布、数据漂移
Agent 决策审计 工具调用格式、参数类型、预算超限 决策链路合理性、目标达成度 幻觉工具调用、目标偏移
文档生成 标题层级、必填段落、链接有效性 术语一致性、受众适配度、示例可运行性 过度营销语、事实核查

6. 总结与行动建议

6.1 核心心法

  1. 判断要分层：确定性的事交给规则引擎，语义的事交给 LLM，兜底交给独立反思
  2. 规则即数据：YAML 落盘、版本管理、可离线测试、可 CI 集成 —— 这是基础设施思维
  3. 证据链要完整：每层产出可追溯，Layer1 给位置，Layer2 给理由，Layer3 给异议
  4. 成本要可控：Layer1 零成本，Layer2/3 按需开启，环境变量一键切换

6.2 立即可用

6.3 贡献规则

一句话总结：把质量门禁从”请大模型打分”重构为”规则引擎快筛 + LLM 语义判断 + 独立反思复核”的三层漏斗，是 LLM 工程化落地的关键一步 —— 好系统不靠模型聪明，靠架构兜底。
