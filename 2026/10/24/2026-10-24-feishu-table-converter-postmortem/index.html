修了三个 Bug 后，我们把它整个删了——飞书表格「兼容性转换」完整复盘

发表于2026-10-24|更新于2026-10-29|工程实践

一个基于错误前提的「兼容性转换层」，修得越正确，破坏越大。在写任何转换逻辑前，先用 10 行探针验证下游是否真的需要它。

1. 缘起 — 为什么会有这个转换器

我们用 Hermes Agent（一个自研的 Agent 框架）通过飞书机器人向团队推送每日简报、盘中复盘、QGS 质量门禁报告等。飞书富文本消息（post 类型）内部使用 Markdown 元素渲染。

最早有人观察到：「飞书不支持管道表格 | --- |，必须转成 +---+ 文本表格才能正常显示。」为了解决这个问题，我们在 feishu-format 技能里写了一个 convert_tables()，要求 Agent 手动调用它做转换。

但 Agent 经常忘记加载技能、忘记调用。于是我们把这个转换逻辑硬编码进了 QGS 插件的 _on_transform_llm_output 钩子：每次 LLM 产出，只要带表格就自动转。问题看似解决了。

直到用户反馈：「QGS 报告一出来，表格就只显示原始 Markdown 格式。」更奇怪的是，之前 Agent 手动用技能转换的表格是正常的。

2. 排查与「修复」—— 10 月 18 日的三个 Bug

我们对着磁盘上的 feishu_format.py 单步调试（非记忆复述），发现了三个独立的 Bug：

# Bug 现象 根因 修复
1 对齐冒号漏转 ` :— 、
2 代码块内表格被误转 python\n| col1 | col2 |\n|---|---| 被转成 +---+，污染代码块 缺少 in_code_block 状态标志 加 in_code_block，围栏内跳过转换
3 BLOCK 路径未转换 QGS 拦截消息（评分 < 60）里的表格同理显示为原始 Markdown 只有 PASS 路径（≥60）调用了 convert_tables，BLOCK 分支漏掉 __init__.py line 1447 补上 convert_tables(response_text)

三个修复全部实测通过，7 个用例覆盖：对齐冒号、代码块保护、BLOCK/PASS 双路径、CJK/emoji 单元格、围栏后续正文表格、无分隔线的 | 行。python3 -m py_compile 语法检查通过。

此时我们以为问题解决了。

3. 真相时刻 — 10 月 22 日：前提本身就是错的

复盘时，我写了一个 10 行探针，复制飞书适配器的 _MARKDOWN_HINT_RE 正则（逐字取自 adapter.py line 107–122），对比「原始管道表格」与「转换后 +—+」的嗅探结果：

实测数据

用例 原始管道表格 转换后 +—+
A：纯表格报告（只有表格、无标题/粗体/列表） hint=YES → post(富文本) hint=NO → text(纯文本) ⚠️
B：混合消息（表格 + ## 标题 + **粗体**） hint=YES → post hint=YES → post（但表格变成了无法渲染的 ASCII 线条）

用例 A 是完整降级：转换器把唯一的嗅探信号（管道表格）吃掉了 → 适配器判定无 Markdown 标记 → 强制降级为 text 类型 → 所有 Markdown 格式丢失（表格、粗体、代码块全部不渲染）。

用例 B 是部分损坏：还有 ##、** 等标记，消息类型仍是 post，但 +---+ 在 md 元素里不是 Markdown → 飞书客户端把它当纯文本渲染成一堆 +---+ 线条。而那些因 Bug 1/3「漏转」的表格（带冒号、或在 BLOCK 路径）反而原生渲染成了正常表格。这就造出了诡异的混合状态：越是按规矩转换的表格越丑，漏转的反而正常。

更深层的历史：飞书适配器自己曾经有一段强制降级逻辑——检测到管道表格就强制 msg_type=text（见 hermes-agent issue #52786）。那是因为早期飞书客户端确实不渲染 post+md 表格。后来客户端升级原生支持了，上游把降级分支删了，并加了回归测试（test_feishu_table_markdown.py，已跑通）。我们的转换器是在旧结论上建的庙，而新结论早已推翻旧结论。

4. 踩坑记录 — 反例与边界

反例 教训
修 Bug ≠ 修对方向 三个 Bug 修得再正确，也只是让一个「本不该存在」的组件跑得更彻底。当你在同一个组件上修第 3 个 Bug 时，先质疑组件存在的必要性。
嗅探分发 + 上游重写 = 隐性耦合 任何发生在类型嗅探上游的格式重写，都必须保留嗅探依赖的字段。我们的转换器恰恰吃掉了最强的嗅探信号（管道表格）。
「下游不支持」的结论有保质期 早期「飞书不渲染表格」是真的，但客户端升级了。兼容层应带「过期自检」：每次部署前跑一遍探针，若下游已原生支持 → 直接删除转换器。
自动化管道必须覆盖所有输出路径 PASS/BLOCK/error 等分叉路径，转换逻辑漏掉任意一条 = 该路径输出不受管道约束。Bug 3 正是如此。

5. 总结

核心结论

在写任何「兼容性/归一化」转换逻辑前，先跑一个 10 行探针：

  1. 谁在管道末端决定消息类型/格式？（是嗅探分发吗？）
  2. 我的转换会改动嗅探依赖的字段吗？
  3. 「下游需要这个转换」这个前提，今天用实验验证过吗？

如果 3 答案是「靠记忆/文档/传闻」，不要写转换器，先跑探针。我们的教训是：探针 10 行，转换器 100 行，删除它 1 行。

行动清单

  • ✅ 已删除 QGS 插件中对 convert_tables() 的全部调用（PASS/BLOCK 双路径）
  • ✅ 保留 feishu_format.py 作为参考/备份，不再被调用
  • ✅ 飞书适配器回归测试已锁定在仓库（test_feishu_table_markdown.py）
  • ✅ feishu-format 技能文档已同步更新（references/qgs-auto-conversion.md）：明确标注「QGS 不再转换，飞书原生渲染管道表格」
