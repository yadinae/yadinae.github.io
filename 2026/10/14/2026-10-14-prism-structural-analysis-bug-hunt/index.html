Prism 棱镜扫码 — 在 2419 行代码里找出 11 个人人略过的缺陷

发表于2026-10-14|更新于2026-10-21|工程实践

普通的代码审查（肉眼 + linter）只能看到表面缺陷。我们在 agent-evolution 引擎上用 Prism 结构分析棱镜（Cranot 的 5 个分析技能），在一次 /prism-scan 运行中发现了 13 处带行号的缺陷（含 2 高严重），全部落到代码并修复。本文把 Prism 的思路、找到的真实例子和复用方法写给你。

1. 缘起 — 代码审查做了 3 年，还是没撞见真正的坑

agent-evolution 是我们让 AI Agent 自己进化的引擎：扫描执行日志 → 分类错误 → 拉取修复策略 → 生成改进计划 → 自动 apply → 验证。evolve_analysis.py 单文件 2419 行，负责从 fix_strategies.md 解析修复模板，往 knowledge-base.json 积累教训，往 evolution-plan-*.json 写计划。

我们写 pytest，跑 black，甚至请同事肉眼过了两轮——都没撞见以下几个缺陷：

  • .count('401') 把字符串 "401" 误当 HTTP 状态码
  • hash() 作为去重主键却跨进程随机化
  • _load_knowledge_base 用裸 except: pass 把损坏的 JSON 吞成空字典，随后把空字典写回覆盖原文件
  • 写状态文件非原子写，半写崩溃留下损坏 JSON

这些缺陷从代码上”长得很正常”，只有在某个边界条件命中才翻车。普通 reviewer 又怎么会发现呢？答案是：换一个棱镜(prism)。

2. 核心方法 — Prism 不是“检查清单”，是“动态认知棱镜”

Prism（来自 Cranot/super-hermes）是 5 个 Hermes 技能：

技能 作用 什么场景
/prism-discover 列出 10~20 个可能分析的领域 不知从何下手时
/prism-scan 炒一个专属认知棱镜，然后执行 单文件/单文档深度审查
/prism-full 设计多轮流水线 + 必做对抗性自校 重要模块，值得花成本
/prism-3way WHERE(结构)/WHEN(时间)/WHY(可能性) 三角 + 综合 非代码 artifacts
/prism-reflect 分析分析本身的盲区，写 .prism-history.md 知道自己不能看什么

Prism 的核心区别在两点：

① 棱镜不是固定模板。 /prism-scan 会现炮制定一个针对当前文件的认知棱镜（75–200 词，必须“建构再诊断”），比如 “找出每一个隐式边界（coercion / default / null check），追踪多跳错误分支到用户可见伤害” —— 而不是背诵一份通用 checklist。

② 守恒定律 (Conservation Law)。 每次分析都会推出一条 A × B = 常量 的结构守恒，比如 Prism 在 agent-evolution 上一次扫出的：

正则表达式 × 格式鲁棒性 = 常数（阶段 1）；自动化 × 验证 = 常数（结构性）；文件 I/O × 状态完整性 = 常数

守恒定律不是建议 —— 它揭示了一个工程问题在所有实现上都逃不过的权衡。把守恒定律放在眼前，就能反向推出“什么改进一定会制造新缺陷”，从而扫掉表面光鲜的伪修。

3. 实战 — Prism 怎么把 13 处缺陷藏到明白

Prism 在 evolve_analysis.py 上的第一次扫是 /prism-reflect（自反镜 + 盲区记录）。它既产出缺陷清单，又把 Maximized/Sacrificed/Recommendations 写入 .prism-history.md，为下轮 /prism-scan 引路。

随后两轮 commit (8399fb2 高 2 严 + 698af9c 中 9 低) 把所有缺陷落到代码。以下是 6 个最典型的，每个都来自不同“隐式边界”。

3.1 .count('401') 把日志噪声当真实 HTTP 失败

咱扫日志里的一段错误 ...status=40101... — 字符串里恰好包含了一个 401，瞬间被当作一次 auth 失败，把正常请求记成异常 ×1。Prism 的镜头让它暴露出来： “朴素 .count('401') 只能看到 401 出现的字面形态，却摧毁了 上下文信息 —— 是 state=40101 还是 HTTP 401。后者分支选错，前者则是假阳。”

修复: 词边界 \\b401\\b + 失败特征正则，只统计真实失败信号。

3.2 hash() 作为去重主键 —— 跨进程随机化

知识库去重用 hash()，却无人想到 hash() 在默认 PYTHONHASHSEED 下对 str/bytes/datetime 是随机的。于是同一个缺陧在进程 A 去重后，在进程 B 又重新入库，知识库逐轮 膨胀 而非收敛。Prism 的 temporal simulation 镜头 (Cycle 3: 原作者离) 把它揪出来：“一项依赖进程内隐状态去重的知识累积，没写进文档就等着新人踩坑。”

修复: 规范化 JSON 字符串作为确定性去记键；failure_lessons 保留最旧教训。

3.3 硬编码路径 /home/admin/.hermes vs HERMES_HOME

验证函数硬编了 /home/admin/.hermes，而 apply_safe_improvements 写路径却用 HERMES_HOME —— 两套路径不同步，本地验过“有效”的改进在 CI/他人机器上全部变成“失败”。Prism 的 identity 镜头揪出这个 “声称的身份 vs 实际身份” 鸿沟。

修复: HERMES_HOME / "skills" / cat / name / "SKILL.md"。

3.4 裸 except: pass 把损坏 JSON 吞成空字典 → 随后覆盖原文件

知识库损毁 → 静默返回 {} → 调用方当作“空库”，把空字典写回原路径，把 50 条历史教训彻底抹掉。Prism 的 error resilience 镜头追得很远：“destroyed context = ‘损坏’ 信号本身；wrong decision = 选择‘空默认’而非‘报警+保留’；harm = 下游静默覆盖。”

修复: except (json.JSONDecodeError, OSError) → 备份 .corrupt + 报警，决不返回空覆盖。

3.5 非原子写 → 半写崩溃留下损坋 JSON

修复:tmp + os.replace 原子写；读损坏文件时备份 .corrupt + 重置不崩溃。

3.6 from datetime import 写进循环内

Prism 还抓到**“知识丢失”** (Cycle 1): 每次 loop 都从 import 入口进，新人难以判断 datetime 真正归属何处，易犯搬迁遗漏。 → 模块级导入。

3.7 consecutive_failure 的验证路径缺失

Prism 还指出：检测到 P0 之后没有“验证它是否恢复”的分支 —— 于是增加了 effective / partial / failed 三路验证分支。

4. 踩坑记录 — 用 Prism 需要注意的 3 点

4.1 镜头成本不便宜

/prism-reflect 是 2~3 倍 /prism-scan 的Token —— 只拿值得的模块下镜子。Prism 自己的建议说得最清楚：

“对安全攻击面：/prism-scan with security focus；对时间退化：/prism-scan with temporal focus；对跨文件架构：/prism-full。”

不要对每个文件全科普。在 README.md 或已发布博文上扫一次，换一轮 prism-scan 在 fix_strategies.md —— 这样 .prism-history.md 的 Sacrificed 域才会收敛。

4.2 守恒定律会被曲解

看到 A × B = 常数 容易手撕一张“优化”表，却忽略 常量本身会变。Prism 强调（l12 meta-law）：

“把你的改进当新 artifact，再扫一遍 —— 你的改进掩盖了哪些原问题？那个被掩盖的性质在你改进里又重新显现了？”

举例：我们把 hash() → JSON-string 去重，解决了跨进程随机化，但引入了 json.dumps 时序不稳定的问题 —— 又是一轮对抗。

4.3 .prism-history.md 是增长引擎，不是档案

每次 /prism-reflect 都会 追加到 .prism-history.md；下次 /prism-scan 会读它，并在 Sacrificed 域加权对应视角。不要手动删 history —— 删了相当于忘掉自己之前扫视了哪些盲区。

5. 复用方法 — 5 步把 Prism 安上自己的项目

  1. 装上技能 — hermes skills install prism-scan prism-full prism-3way prism-discover prism-reflect (源自 Cranot/super-hermes)。
  2. 探索领域 — /prism-discover 你的 main.py，拿 10~20 个分析维度菜单。
  3. 挑值一棍 — 选“错误恢复” / “时间退化” / “跨文件架构” 这样结构性的维度扫 /prism-scan（带 --focus="..."）。
  4. 留约 — 每次扫完立即 /prism-reflect，把 CONSTRAINT REPORT 写进项目 .prism-history.md，惠及下次。
  5. 验证-对抗-修复循环 — 把 Prism 给的缺陷落为 pytest 用例 → 修复 → 要求它扫改动后的文件，确认没掩盖一手。

6. 总结

我以前以为 Prism 教会我的
代码审查靠肉眼 + linter 结构缺陷藏在“隐式边界”里，肉眼看不见
守一次 review 就够 守恒定律告诉你：任何改进都会制造新缺陷
去重/缓存随便写 hash()、原子写、确定性键 —— 跨进程/跨机都要意识到

Prism 的价值，远不于“给你 checklist”。它是一台能看到自己盲区的审查机 —— 用动态棱镜替换固定眼光，用守恒定律取代肉眼直观。在 agent-evolution 上扫一次，就从 2419 行代码里捞出 13 处藏了 3 年之久的缺陷。

如果你也在写一个 LLM 驱动的自进化引擎/管线，强烈在第一次 git push 前跑一次 /prism-reflect —— 它可能会把一个“应该能跑”的 release 变回“等我修完最后一个裸 except”。
