备份 cron 每天报 ✅，但 clone 出来是空的——我的快照仓库一直在静默丢 1855 个文件

发表于2026-10-31|更新于2026-10-31|工程实践

我每天凌晨 2:30 有个 cron 把整个 Agent 的运行时目录 ~/.hermes 快照到一个 GitHub 仓库，连续跑了三个月，每次报告都是「✅ 备份完成，11134 文件」。直到 10 月 30 号我例行核一个插件的提交状态，才发现：fresh clone 这个备份仓库出来，crew 和 homeassistant 两个插件是空目录，1855 个文件一个都不在。 备份的敌人不是崩溃，是假绿灯——那个每天让你安心的文件计数，本身就是谎报的那一个。

1. 缘起 — 从「改完插件没进 git」查起

10 月 30 号晚上，我给质量门禁插件打了两处补丁：一个交付物截断（防止超长输出撑爆评审上下文），一个给 FAIL 消息加「建议修复顺序」清单。改完跑 smoke test，全绿。

然后按老规矩核提交状态，发现一个尴尬的事实：这两处改动根本不在任何 git 仓库里。

根因不复杂：~/.hermes/ 是运行时目录，不是 git 仓库。仓库里存的是 hermes_backup/ 快照副本，两者靠每天 2:30 的 cron 快照同步，不是实时镜像。改完 live 插件到下次快照之间，那段窗口期改动是裸奔的。这个教训值得单独记一条：

改 ~/.hermes/ 下的文件 ≠ 已提交。 改完必须立刻 git add 对应文件，不能等 cron「赌一把」。

但它只是引子。顺着「快照到底靠不靠谱」往下挖，我撞上了真正让我后背发凉的东西。

2. 核心方法 — 三个层层递进的坑

坑一：运行时目录和 git 仓库是两回事（上面这条）

这条最直接。解法是把「改完即提交」固化成习惯，而不是依赖周期性快照兜底。快照是备份，不是版本控制，两者窗口期完全不同。

坑二：备份工作区里有嵌套 .git，git add 生成了 gitlink

这是本次真正的坑。我的备份脚本逻辑是：把 ~/.hermes 的几个目录拷进备份仓库工作区，然后 git add -A && git commit。

问题出在插件目录。crew 和 homeassistant 这两个插件是就地 git clone 装进来的——它们的目录里各自带了一个 .git。而备份脚本里有个 rsync 分支：

我的机器上 rsync 根本没装（command -v rsync 为空），所以永远走 cp -a 兜底分支——它把嵌套的 .git 目录原样拷进了备份工作区。

于是 git add -A 看到 backup/.../plugins/crew/ 里有个 .git，就把它当成一个内嵌 git 仓库，记录成一条 gitlink（mode 160000）——只存一个 commit 指针，不存任何文件内容。git 当时还打印了警告：

但 git add -A 的输出没被捕获、没被检查，这个警告就石沉大海了。

坑三：cron 报告用 find 计数，谎报了「完整性」

最要命的一环。备份 cron 的报告里那句「✅ 备份完成，11134 文件」，是这么算出来的：

它数的是磁盘上有多少文件，不是 git 里跟踪了多少。而真实情况是：

口径 数字 含义
find 工作目录文件数 11134 cron 报告里那个让你安心的数字
git 实际跟踪的文件（bash 对象） 9279 git ls-tree 里 mode 为 100xxx 的条目
gitlink 条目（160000） 16 每个只存一个 commit 指针
静默丢失的文件 1855 正好等于 16 个 gitlink 目录里的文件总数

11134 − 9279 = 1855，和那 16 个 gitlink 目录里的文件数完全吻合。监控指标（文件计数）本身就是谎报的那个——这是假绿灯最危险的地方：你盯着的那个数字，恰恰是骗你的那个。

4. 踩坑记录 — 边界与修复

影响范围比想象的窄，但性质比想象的糟。 时间线：

  • 10-07 起，7 个 homeassistant gitlink 首次出现（那时插件就带着 .git 装进去了）
  • 10-31 跳到 16 个（crew 插件装了 5 份 profile 副本，全带 .git）

而这篇文章写到一半，事情升级了。

10:17 我还能读到 plugins/crew/install.py 的内容；10:28，plugins/crew/ 整个目录从运行时目录里消失了（plugins/ 的 mtime 停在 10:28:20）。五个 profile 副本一起没。至于是谁删的——我没能定位到具体命令，不编故事。

真正让我确认这套备份是空心的，就是这一刻：

git 里存的是 gitlink，一个 commit 指针，零个文件。也就是说——如果这台机器今晚就没了，我拿这份「✅ 已备份 11134 文件」的仓库恢复出来的，crew 和 homeassistant 就是两个空目录，而恢复脚本一声不吭（cp -a 拷空目录不会报错）。

最后是把 crew 从上游重新 clone 回来才补上的。上游 github.com/macd2/Crew 是公开的，而 .install-metadata.json 里正好记着 pinned revision d81551a2——和上游 HEAD 严丝合缝对上，244 个文件一个不差。homeassistant 同理，github.com/NousResearch/hermes-homeassistant 也是公开仓库。

但请注意这里有多侥幸：它能救回来，纯粹是因为我知道该去哪救、且元数据恰好记着 commit。 备份的全部意义就在于——真出事的时候你不需要知道上游在哪。一个 git clone + _restore.sh 的干净恢复，会静默地给你两个空插件。而且那份本地副本里还有一个我改过的文件（scripts/crew_graph_serve.py）和两个运行时 db，纯上游恢复捞不回来——这是「备份 ≠ 上游」最直白的注脚。

再补一条自检，让它下次不可能再静默过关——git add 之后当场对账，差值非零就 exit 1，而不是照常在报告里写 ✅：

这条自检本身有两个坑，我第一次写的时候两个都踩了，踩任何一个都会天天误报，然后你就会把它关掉——那就等于没有：

  1. git ls-files 必须带目录参数。 不带参数数的是整个仓库（这篇博文的 .md、封面图、笔记全算进去），拿它跟只数 $BAK_DIR 的 find 比，差值恒为正且毫无意义。实测在那个假绿灯 commit 上：find hermes_backup = 9290，git ls-files 全仓库 = 9602——照这个写，门禁每天红。
  2. find -type f 不数符号链接，git 数。 技能目录里有 11 个 symlink，于是差值恒等于 11，永远对不上。要用 find \( -type f -o -type l \)。

顺带一个反向的惊喜：在同一个 commit 上 checkout 出来数，find 得 9290、git ls-files 里的 blob 也是 9290，而 gitlink 是 16 条——说明那 16 个目录在 clone 出来时就是彻底空的，一个文件都没有。数字自己对上了自己。

落实的时候，又挖出两个同类假绿灯

文章写完不等于问题修完。真去改脚本时，同一个「看起来成功」的毛病还在另外两处：

其一：cron 侧跑的永远是旧脚本。 cron 不直接跑仓库里的脚本，而是先跑一个 wrapper，wrapper 再 exec 仓库内主体脚本——但它只 clone、不 pull。也就是说你 push 了修复，今晚跑的还是昨天的版本。更绝的是 hermes_backup/ 里 gitlink 时代遗留的未跟踪文件会挡住 --rebase/ff-only 合并，让仓库无声停在旧 commit。两个细节：清理要 git clean -ffdq（两个 f——单个 -f 时 git 拒绝进入含 .git 的目录，正好就是这批遗留目录）；pull 失败必须打到 stderr 并给出命令，不能静默继续。

其二：推送失败也打印「✅ 备份完成」。 原脚本 push 失败时置一个 push_msg="⚠️ 推送失败"，然后照常往下走，末尾照样输出 ✅ Hermes 备份完成。落地的只有本地 commit，远端什么都没有——而 cron 报告是绿的。改成 push 失败直接 exit 1，标题换成 ❌ 备份未完成。

顺带把「落后/分叉」的处理挪到重建快照之前：快照工作区每次整体重建，远端就是历史的事实来源，落后就硬重置到 origin/main（前提是 hermes_backup/ 以外没有未提交改动，避免误伤手工写的博文）。原来那段 git pull 写在拷贝之后，一旦本地攒出推不掉的快照提交，之后每次备份都会静默失败。

（顺带一提：装上 rsync 也能治本——脚本里本来就有 --exclude='.git' 的 rsync 分支，只是这台机器没装，永远走不到。我试着装，dnf install rsync 直接 segfault（Alibaba Cloud Linux 3，exit 139），所以别指望这条路：兜底分支自己得是对的，不能把正确性押在「另一个工具存在」上。）

5. 总结

一句话：备份系统的头号敌人不是崩溃，是「看起来成功」。 崩溃会让你立刻去看日志；假绿灯会让你在三个月里每天看着 ✅ 睡好觉，直到某天真的要从备份恢复，才发现一半是空的。

五条可带走的 takeaway：

  1. 改运行时目录 ≠ 已提交——live 文件和 git 仓库是两回事，改完立刻提交，别指望周期快照。
  2. git add -A 遇到内嵌 .git 会生成 gitlink——只存 commit 指针不存内容，clone 出来是空目录。装插件/拷目录前，先 find -name .git 扫一遍，或在 git add 前剥掉。
  3. 对已是 gitlink 的路径，光剥 .git 不解决问题——必须先 git rm -r --cached 把它请出 index，git 才会重新按普通目录扫描。
  4. 对账门禁自己也会写错——git ls-files 要限定目录、find 要连符号链接一起数，否则误报到让你想关掉它。
  5. 验证备份的唯一方式是真恢复一遍——git clone 到临时目录，数关键目录的文件数，0 就是空心。对账 find 计数 vs git ls-files 计数只是日常哨兵，不能替代真恢复。

还有一条元教训：修完要沿调用链再走一遍。 我改的是仓库里的主体脚本，但 cron 跑的是 wrapper 间接调用的那份——中间隔着一层不 pull 的 clone。真正让修复生效的，是把 wrapper 也改掉之后那次运行。

监控指标里最容易自欺的那一个，往往是你最放心看的那一个。

本文所有数字均来自对备份仓库真实 commit 的实测：假绿灯快照 14752aaa 上 16 个 gitlink 条目、9279 个被跟踪 blob、1855 个被吞文件，git clone 到临时目录复现出 0 文件的空目录。修复后重新备份并再 fresh clone 验证：gitlink 0 条、plugins/crew 244 个文件、plugins/homeassistant 14 个文件、嵌套 .git 0 个。

顺带把前面那句”本地独有改动捞不回来”落到实处：从上游重新 clone 回来的 crew，git status 干净、和 d81551a2 一字不差——那个我改过的 scripts/crew_graph_serve.py，改了，然后永久没了。它当时只活在 gitlink 覆盖的目录里，备份里一个字节都没留下。这就是空心备份的最终账单，不是我推演的风险。
