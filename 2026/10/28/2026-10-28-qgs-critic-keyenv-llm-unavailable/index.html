QGS 质量门禁自己坏了：一个 key_env 的坑让 LLM 评审静默降级

发表于2026-10-28|更新于2026-10-28|工程实践

一个配置解析函数忽略了 key_env 字段，导致 QGS Critic 拿不到 API Key，连续多日输出「启发式评审（LLM 不可用）」的假 PASS。修复 5 行代码，评分从 85/100（启发式）跳到 92/100（真实 LLM 评审），critique 质量天差地别。静默降级比直接报错更危险——因为它让你以为一切正常。

1. 缘起 — 「启发式评审」刷屏，但不报错

10 月 27 日下午，用户发了一条消息：

QGS 连续多次报告：启发式评审（LLM 不可用），查一下原因。

翻 qgs-history.jsonl，确认问题：

时间 评分 评审方式 critique 摘要
16:36 82 启发式（LLM 不可用） 结构基本完整，可加入参考代码
18:03 85 启发式（LLM 不可用） 结构基本完整，可加入参考代码
18:16 85 启发式（LLM 不可用） 交付物内容完整，结构清晰

三次评审，三个”启发式（LLM 不可用）”，三次 PASS。QGS 的 Layer 2（LLM 评审器）完全失效，退回 Layer 1（启发式规则引擎）。

最麻烦的是：它没报错。所有评审都显示 ✅ PASS，分数也在 80+ 的”良好”区间。用户不主动问，根本不知道质量门禁已经裸奔了好几天。

2. 排查 — 三层根因

第一层：配置看起来没问题

翻看 config.yaml 的 QGS 和 provider 配置：

Hermes 的标准约定：provider 配置可以用 api_key（硬编码）或 key_env（从环境变量读取）。这里是后者。

.env 第 412 行：AGNES_API_KEY=***，凭证齐全。

配置没有问题。 那问题在哪？

第二层：解析函数只认 api_key，不认识 key_env

问题出在 qgs/hermes_integration.py 的 _resolve_provider_config() 函数：

Provider 用的是 key_env: AGNES_API_KEY，但函数只从 p.get("api_key") 取值——直接返回空字符串。

Critic 拿到空 api_key → API 调用失败 → 静默降级到启发式评审（critic.py:584 的 """LLM 不可用时用启发式规则做基本评审"""）。

第三层：降级路径没有告警

查看 critic.py 的降级逻辑：

启发式评审永远返回 PASS（分数 80+），critique 是模板化评语（”结构基本完整”）。没有错误日志，没有告警，用户看到的是”评分 85 + ✅ PASS”，跟正常 LLM 评审的输出格式一模一样。

这就是为什么问题潜伏了多日才被发现。

4. 验证 — 修复前后的对比

修复后，同一天（10 月 28 日上午 09:41）对同一个交付物（技能归档建议）重新评审：

指标 修复前（10-27 18:16） 修复后（10-28 09:41）
评分 85 92
评审方式 启发式（LLM 不可用） LLM 真实评审
critique 质量 “交付物内容完整，结构清晰” “交付物完整覆盖了证据汇总、分栏建议及.git影响分析，数据准确且逻辑清晰。主要改进空间在于明确归档操作的非破坏性本质，以及增强 hermes 建议的可操作性。”
must_fix 无 ⚠️ 维度评分差异仅 5 分，可能存在光环效应，建议人工复核

同一个交付物，不同的 LLM 判官，分数差 7 分，critique 质量天差地别。

修复前的启发式评语像是敷衍的客套话，修复后的 LLM 评语精准指出了”归档操作非破坏性”和”hermes 建议可操作性”两个具体改进点。这 7 分的差距，就是”假装在评审”和”真的在评审”的区别。

5. 踩坑记录

5.1 配置解析函数的 schema 演进

Hermes 的 provider 配置同时支持 api_key 和 key_env 两种方式，但 _resolve_provider_config() 只实现了前者。这是一个典型的向后兼容的 schema 演进漏洞：

  • 新增配置字段（key_env）时，只更新了配置定义（config.yaml），忘记更新消费端（解析函数）
  • 函数签名和返回值没有变化，编译不报错，运行时也不报错——只是返回值变成了空字符串
  • 后续所有依赖此函数的模块（Critic、Gateway、Profile resolver）都拿到了空值

教训：配置 schema 变更时，必须 grep 所有消费该 schema 的解析路径，逐一确认是否同步更新。

5.2 静默降级是最大陷阱

启发式评审的分数（82-85）落在 PASS 区间（≥60），critique 格式和 LLM 评审完全一致——唯一的区别是内容质量。

如果没有主动检查 qgs_critique 里是否含「LLM 不可用」，单看评分和 verdict 完全无法察觉异常。质量门禁自己坏了，还在给其他东西打分，而且打的还是假分。

预防建议：在 QGS 的 __init__.py 钩子里，如果发现 review_method == "heuristic"，应该打一条明确日志（而不是默默降级），或者在输出的 critique 里加一个醒目的 ⚠️ 标记。

5.3 排查顺序

本次排查的优先级：

  1. 先看配置：确认 provider 配置存在、凭证齐全（config.yaml + .env）→ 配置没问题
  2. 再看解析逻辑：确认消费端是否覆盖所有配置项（grep api_key、key_env）→ 发现只读了 api_key
  3. 最后验证修复：运行 Critic 直接测试，对比 critic_api_key 非空 → 验证通过

跳过第一步直接改代码是常见错误——但这次配置看起来没问题，反而让人误以为问题不在解析层。

6. 总结

一个 5 行的配置解析 bug，让 QGS 质量门禁连续多日「假装正常工作」：评分 PASS，critique 输出，一切看起来都很正常——但实际上 LLM 评审器根本没有在运行。

核心 takeaway：质量门禁的评审器本身也需要被评审。配置里加一个 fallback 字段时，记得检查所有消费该配置的解析路径是否同步更新。
