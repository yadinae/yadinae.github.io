重复的决策不该重复花钱 — LLM 决策缓存 sidecar 实战与三个反直觉的坑

发表于2026-10-07|更新于2026-10-10|AI 工程实践

一句话摘要：把 LLM 决策当作纯函数做本地记忆化，重复决策 0ms、0 成本——但真正的难点不是”怎么缓存”，而是”什么绝对不能进缓存”。

1. 缘起 — 免费模型的 429 把我逼出了本能反应

今年 9 月，我的 Agent 管线全面切换到免费 LLM 路由。省了钱，但也迎来了新的老师：429 Too Many Requests。限流一来，定时任务超时、批量分析中断，最惨的一次每日综述跑了 3600 秒最后吃了个超时。

抱怨之余我注意到一件事：我发出去的请求里，有相当一部分问的是同一个问题。每小时的仓库监控、每次流水线的质量门禁、每个批次的同构检查——状态没变、问题没变、模型没变，答案理论上就该一模一样。这些调用在烧同样的 token、排同样的队，产出的却是可以复用的旧答案。

这不就是经典的**记忆化（memoization）**问题吗？函数式编程里”纯函数结果缓存”玩了几十年，只是把函数换成 LLM 调用而已。于是我接入了 jevcache——一个本地决策缓存 sidecar，用它把”决策 ≈ 纯函数 (model, schema, state)“这个假设落了地。本文记录整条链路的搭建、实测数据，以及三个让我改了两次架构的反直觉的坑。

2. 核心方法 — 三层 sidecar，指纹做键

2.1 架构：缓存层夹在调用方和 LLM 之间

关键设计只有三条，但每条都是踩过坑才确定的：

  1. temperature=0。缓存的前提是可重放——同一输入必须产生同一输出，否则缓存的就是噪声。adapter 里强制写死 temperature: 0，调用方改不了。
  2. 指纹 = sha256(model ⊕ schema ⊕ canonical(redact(state)))。canonical 序列化保证 JSON 键序不影响命中；PII 脱敏在哈希之前做（后面第 3.2 节有实测）。
  3. 只有成功的答案进缓存。这是全文最重要的一条，见 3.1。

2.3 实测数据（2026-10-07）

搭建完成后我跑了一轮全链路验证，/stats 的真实返回：

  • 首次 POST /decide → miss，adapter 调模型后返回 {"answers":{"q":2}}
  • 完全相同的第二次调用 → "cached":true，毫秒级返回，指纹逐字节一致
  • 服务经 systemd 常驻（jev-adapter / jevcache-serve 均 active），全部绑定 127.0.0.1

单次省的钱（$0.0002）不起眼，但这类决策的特征是高频重复——每小时的监控、每批次的门禁，一天几十次同构调用叠起来，命中率会决定账单形状。

3. 踩坑记录 — 三个反直觉的发现

3.1 最大的坑：不是”怎么缓存”，而是”什么时候不能缓存”

这是全项目最值钱的一条经验。我最初把雪球文章管线的质量门禁接了进去，想着”数字校验问题天天问，缓存稳赚”。实测两天：2 次 miss，0 次 hit。

根因一想就明白：门禁的 state 是文章里的数字 + 当天的行情快照——每天全变。指纹跟着 state 走，天天 miss，缓存价值为 0，白养了两层服务的复杂度。

由此我总结了一条接入判据，之后所有”要不要加缓存”的评估都先过这道筛：

高频（日级几十次以上）× 决策重复（参数组合稳定），两个条件缺一不可。
低频的、state 每天全变的决策，不接。

反过来说，缓存还有一个更阴险的逆操作风险：如果 state 其实变了但你没让指纹感知到，命中就意味着”跳过了对新鲜数据的判断”。雪球门禁在 09-21 事故后已经以程序化校验为权威，再套一层 LLM 决策缓存，等于给”跳过新鲜判断”开了后门。有些正确性不能用缓存换性能。

3.2 PII 必须在哈希前脱敏，否则缓存会分裂

同一个风控问题，state 里只差一个邮箱：

实测两次调用返回完全相同的指纹——脱敏发生在哈希之前，不同用户的同构问题命中同一条缓存。如果反过来先哈希后脱敏，缓存会按 PII 无限分裂，命中率归零；更糟的是缓存账本（ledger）里会存下明文 PII。顺序错了，缓存从资产变成负债。

3.3 官方文档没写的三个文件格式陷阱

接入时在 schema 加载上耗掉了半天，记录下来给后来者避坑：

  1. 文件 schema 加载不可用：./jevcache.schemas.json、~/.jevcache/schemas/*.json，写了 8 种 JSON 结构全部静默跳过（不报错，就是不加载）。能用的只有两条路：① HTTP API 内联 schema ② publish/add bundle 文件。
  2. questions 必须是 dict 形式 {qid: prompt}，写成数组或纯字符串直接校验失败——文档里没写，报错信息也看不出来。
  3. 默认端口撞车：官方默认 JEVCACHE_LOCAL_URL 指向 8080，而本机 8080 早被别的服务占了，sidecar 显式改到 8123 才跑通。JEVCACHE_DIR 对文件 schema 加载同样无效，但 ledger 日志会正常写进去。

一句话总结这类坑的共性：新工具的”配置面”往往是文档完成度最低的地方，二进制能跑 ≠ 加载链路能通，每个配置项都要用最小用例实测。

4. 总结

  • 核心结论：LLM 决策缓存的收益公式是 命中率 × 频率，而命中率由”state 是否重复”决定——先判据，后接入，别把 sidecar 架在每天全变的状态上。
  • 一条铁律：降级答案（429/超时/兜底文本）永不进缓存。缓存里只能有模型健康时的原答案，否则一次限流会污染之后所有的决策。
  • 一句话 takeaway：缓存不是加速器，是”我相信这个答案不会再变”的押注——押注前先想清楚什么情况下它会变。
