AI 画不出一句对的话 — 我把封面、插图、视频都改成了 HTML 渲染

发表于2026-09-30|更新于2026-09-30|技术实践

AI 画不出一句对的话 — 我把封面、插图、视频都改成了 HTML 渲染

一句话摘要：文字不会乱码、产物可以 git diff、坏一块只重做一块 —— 用「HTML 中间表示 + Playwright 截图 + ffmpeg 拼接」这一套，同时供出了博客封面、文章插图和课程视频，边际成本为零。

1. 缘起 — 三个都被”文字”卡住的场景

过去半年，我在三个完全不同的场景里撞上了同一堵墙：

场景一：带标题的封面图。 用文生图模型做产品封面，中文标题永远是重灾区 —— 多笔画的字糊成一团，凭空多出或少掉笔画，有时整行字变成外星文。最后定下的规矩很朴素：AI 生图只做纯视觉背景（无文字），所有带文字的图走排版。

场景二：博客封面风格杂糅。 首页有的文章配 Unsplash 外链图、有的配 AI 生成图、有的配程序化绘图，色调彼此打架。我需要的不是”更会画的模型”，而是一个统一规格（1200×675 OG 标准）+ 统一版式库的东西。

场景三：教案变成视频。 灵犀学堂的教案要喂给 Lumen 管线生成 YouTube 课程视频，而课件画面几乎全是文字卡片、流程图、要点列表 ——「第四章第三个过程」这种精确文字，AI 视频生成器同样无能为力，还按秒计费。

三个场景的共同点被我后来总结成一句话：我的视觉内容本质是「文字 + 版式」，不是摄影。

而浏览器，恰好是这个星球上最强的文字排版引擎。

2. 核心方法 — HTML 作为视觉中间表示

2.1 为什么是 HTML，而不是让模型直接出图

需求 AI 生图 HTML → 截图
文字精准 ❌ 中文高频乱码 ✅ 浏览器排版，零容错
可复现 ❌ 同 prompt 不同结果 ✅ 同模板同输入 = 同像素
可版本控制 ❌ 图片没法 diff ✅ 模板就是代码，git diff 一目了然
局部修改 ❌ 重抽一次全凭运气 ✅ 改一行 CSS 重截一张
边际成本 按张/按秒计费 ✅ 本地 Playwright + ffmpeg，0 元

分工因此变得非常干净：LLM 负责”写什么”（脚本、文案、数据 JSON），HTML+CSS 负责”长什么样”，Playwright 负责”拍下来”，ffmpeg 负责”拼起来”。 每一层都能单独重跑，不牵一发动全身。

（这张插图本身就是用文中第 2.3 节的管线生成的 —— 数据 JSON 喂给图表模板，一次渲染到位。）

2.2 封面：版式 × 主题矩阵

generate_blog_cover_v2.py 把封面拆成 8 种版式（H01–H08）× 6 套主题 = 48 种组合，输出 1200×675（OG 标准），底层是一个 Playwright 渲染器 render_social_card.mjs。这条管线已经产出 76 张封面（含本文这张）入库，全站封面风格由此锁死。

截图工具 html2img.py 里有一段值得抄走的防御性设计 —— 模板加载的 fallback 链：

批量生产时，”模板没找到”如果静默降级成空白图，你会在三天后才发现一整批封面是废的 —— 宁可退出，不可静默。

2.3 插图：数据即代码

generate_illustration_v2.py 走同一条渲染链，但输入换成数据 JSON，内置 6 种图表版式（bar / kpi / matrix / ledger / pipeline / beforeafter），输出 1200×800。文章里的排行、KPI、前后对比，改一个数字重跑一次即可，不用重新画图。

2.4 视频：时间线 HTML → 定点截图 → xfade

这是三条管线里最有意思的一条。scene-recorder.js 的开头写着当初的核心决策：

机制四步：

  1. buildScenes(script)：把脚本 sections 映射成场景对象（hero / cards / flow / content / closing），每个场景带自己的 duration；
  2. buildPageHTML(scenes)：把所有场景塞进单页 1920×1080 HTML，内嵌时间线数组 TL 和一段 requestAnimationFrame 循环按秒切换 .on 类，另加 4 层视差背景（深度 0.5/0.7/1.0/1.15）；
  3. Playwright 定点截图：打开这一页，按每个场景的 duration 实时等待，到点 page.screenshot() 拿一张 PNG —— 全程只开一次浏览器；
  4. ffmpeg xfade 链：N 张 PNG 两两串接成片。

转场不是随机的，而是按下一场的内容类型挑：

实测数据（今天现场跑的 demo：5 个场景，目标总时长 21.5s）：

指标 实测值
定点截图（含实时等待） ~30s
ffmpeg xfade 拼接 57s ← 真正的瓶颈
总耗时 87.2s
产出 0.7MB / 1920×1080 / h264 / 24fps / yuv420p
成片实际时长 17.5s = 21.5 − 4×1s

两个反直觉的点：

  • 截图不是瓶颈，xfade 串行滤镜链才是。 每多一个场景就多一级滤镜、多一路 -loop 1 输入，耗时线性增长。场景数上去了，要么接受等，要么降分辨率/framerate。
  • 成片比目标短。 每段 1s 的转场会吃掉 1s 素材，总时长 = Σduration − (n−1) × fade。做定时长视频（Shorts 卡 60s）时必须把这笔账算进去。

2.5 局部重生成：HTML 的可寻址性红利

Lumen 侧还有一层 scene-repair-service，暴露 POST /api/content/:productionId/scenes/:sceneId/regenerate —— 只重生成某一个坏场景并重建、复审，而不是整条管线重跑（另有 PATCH 接口改场景内容本身）。因为场景是可寻址的 HTML 片段，改哪儿截哪儿。这条对”AI 产出 10 个场景坏 1 个”的批量内容生产，是成本数量级的差别。

3. 踩坑记录

3.1 xfade 不会告诉你它输出了 yuv444p（静默坑）

教训：“命令成功退出” ≠ “产物可用”。 关键属性（像素格式、时长、分辨率）要用 ffprobe 断言，不能只看退出码 —— 这和”LLM 返回了 200 不等于内容合规”是同一个道理。

3.2 字体文件坏了，中文全是方框

系统里的 NotoSansSC-Bold.ttf / NotoSansSC-Regular.ttf 已损坏，Pillow 报 unknown file format，中文渲染成一排方框。解法是改用可变字体 NotoSansSC-VF.ttf。

HTML 路线有同类风险，只是更隐蔽：浏览器找不到字体会静默 fallback 到另一个字体，排版宽度全变、截出来的图和你在编辑器里看的不一样。渲染前务必 document.fonts.ready + 确认目标字体真的加载成功。

3.3 逐帧录制 vs 定点截图 — 我们自己的演化路线

我们的工具箱里两条路线都活着，对比很直观：

  • 旧方案 html2video.py：Playwright 15fps 逐帧截图 + ffmpeg 编码。要等 CSS 动画真实播完一整遍，慢，且长视频成本高；
  • 新方案 scene-recorder.js：每个场景只在动画到位后截 1 张，切换交给 ffmpeg 转场。

什么时候仍然必须逐帧：场景内部有必须逐帧保留的动画（曲线逐点绘制、粒子效果）。而我们的课件型内容几乎都是”静态构图 + 场景切换”，定点截图完全够用 —— 这是一个”先看内容形态，再选渲染策略”的判断，不是无脑选快的。

3.4 这个方法什么时候不适用

  • 照片、人物、复杂视觉意境 → 还是交给文生图，且遵守”纯视觉无文字”；
  • 已有图片的更新 → Cloudflare CDN 可能缓存旧版长达 4 小时，别原地覆盖，加 -v2 后缀重命名推送；
  • 自由布局的示意图 → HTML flex/grid 表达力有限，复杂拓扑还是得 SVG / 绘图库；
  • 单张一次性图片 → 直接让模型画更快，模板化只在重复生产时回本。

4. 总结

Takeaway：内容型视觉 = 文字 + 版式，那就别让模型去画文字，让它去写 HTML。

落地顺序建议：

  1. 先挑最痛的一条视觉管线，做 3 个版式就够（不必像我这样堆到 8×6）；
  2. 模板加载必须有 fallback 且失败即退出，不做静默降级；
  3. 渲染层固定（同一浏览器、同一字体、同一 viewport），变化只发生在数据层；
  4. 产物用 ffprobe / 尺寸断言验收，不看退出码；
  5. 批量场景按可寻址片段组织，坏哪儿重生成哪儿。
