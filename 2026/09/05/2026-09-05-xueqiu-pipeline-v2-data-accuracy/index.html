让代码写数据，让 AI 写分析——雪球文章管线 v2 数据准确性加固实战

发表于2026-09-05|更新于2026-09-11|AI 工程实践

一句话摘要：当 LLM 不可信时，把数据渲染从 LLM 手里拿走——让代码做它擅长的事，让 AI 做它擅长的事。

1. 缘起 — 一篇「看起来对」的错文章

8 月初，我们的雪球自动发帖流水线 v1 上线了。LLM 拿到 JSON 快照，自己组织语言，自己写数据，自己发布。

一开始运转良好。直到有一天读者评论：

“上证指数收报 3986.31？我看到的是 3930.12 啊。”

我去查——LLM 把上周的指数数据和本周的混在了一起。更隐蔽的是，它还把涨停家数从 57 个「四舍五入」成了 60 个，因为觉得「57 家」不够「整」。

这些错误有三个共同特征：

  1. 读者很难发现——数字看起来合理，只是「不太对」
  2. LLM 不认为自己在犯错——它只是在「合理推断」
  3. 检查成本极高——每篇 2000 字里有 30+ 个数字，逐个核对不现实

这是 LLM 在数据密集型内容中的经典困境：它擅长写漂亮的文章，但不擅长写准确的数字。

2. 核心方法 — 职责分离：代码管数据，AI 管分析

我们重新设计了管线架构，核心原则只有一条：

数据事实由代码渲染，LLM 只负责分析和解读。

2.1 事实块：程序化渲染的「只读数据区」

事实块是整个架构的核心。它是一段由代码从快照中直接提取并格式化的文本，嵌入 LLM 的 prompt 中：

注意几个设计细节：

  • 必须原样引用，不得修改任何数字——这是 prompt 级别的硬约束
  • 数字格式化由代码完成——LLM 看到的已经是格式化好的文本，不需要自己计算
  • 无数据的段落直接不出现在事实块中——LLM 看不到数据，就不会编造「数据暂缺」

2.2 LLM Prompt：从「生成文章」降级为「写分析」

v1 的 prompt 是：「根据以下 JSON 数据，撰写一篇专业的财经评论文章。」

v2 的 prompt 变成了：「根据以下【数据事实块】，撰写分析和解读。所有数字必须与事实块完全一致。」

关键差异：

LLM 从「数据生产者」降级为「数据解说员」。

3. 踩坑记录 — 三个血泪教训

坑 1：LLM 不是「故意」犯错，而是「习惯性」犯错

v1 初期我们以为加一句「请确保数据准确」就够了。结果 LLM 在 80% 的文章中仍然会微调数字——不是故意的，而是它的训练数据中「合理的数字」比「准确的数字」权重更高。

教训：对数据准确性的要求不能靠 prompt 约束，必须靠代码强制。

坑 2：北向资金是僵尸数据

我们发现同花顺的北向资金接口返回的是 2024 年 8 月 19 日之前的旧数据（官方从那天起停止披露每日净流入），但接口依然返回「正常」数据。LLM 会把两年多前的数据当作今天的来写。

教训：数据源的元信息（是否过期、是否真实）和数据本身一样重要。

坑 3：LLM 的「合理推断」是最危险的错误

最可怕的不是 LLM 编造完全不存在的数字，而是它基于真实数据做「合理推断」——比如把 57 家涨停改成 60 家「取整」，把 3930.12 改成「接近 4000 点」。

这种错误肉眼几乎看不出来，读者也不太会去核实，但长期积累会损害账号的可信度。

教训：verify_numbers 的校验阈值必须设得很严（指数价格误差 > 0.01 即报错），不能给「合理误差」留空间。

4. 总结

核心 takeaway

当 LLM 的能力边界和任务需求不匹配时，不要试图通过 prompt 工程修补——重新划分职责。

让代码做代码擅长的事（数据提取、格式化、校验），让 LLM 做 LLM 擅长的事（分析、解读、表达）。这不是 AI 能力退化，而是系统工程的合理分工。

架构适用场景

这个模式不仅适用于财经文章，适用于所有「AI 生成内容中包含关键数据」的场景：

  • 财报解读：数据从 API 拉取，LLM 只写分析
  • 市场报告：指数/成交量由程序渲染，AI 写趋势判断
  • 数据仪表盘文案：数字由代码填入模板，AI 生成解读段落
  • 学术论文辅助：实验数据由代码输出，LLM 帮写讨论章节
