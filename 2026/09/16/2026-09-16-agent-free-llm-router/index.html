我的 Agent 现在 0 花费跑 LLM：四款免费模型 + 智能路由的搭建记录

发表于2026-09-16|更新于2026-09-30|技术实践

一个 Hermes Agent 每天要跑几十个定时任务、多 profile 协作、还挂着股票分析和飞书机器人，按正常推理费用一个月下来是笔不小的开支。这篇文章记录我怎么把它降到 0 元——不是找一家免费服务商完事，而是搭了一个”免费模型路由层”：4 款免费模型分 4 档，按任务复杂度自动路由，某档挂了自动降级。核心配置就 30 行 YAML，全文给出。

1. 缘起 — muse-spark 把输出截断到只剩 7 个字

9 月 14 晚上，我在 opencode zen 网关上手动加了一个新上的免费模型 muse-spark-1.3-contributor-free，想着反正白嫖，跑跑看。

结果当天就开始出问题。翻 gateway 日志能看到原话（我发给 agent 的消息）：

“把默认模型改成 Nemotron 3 Ultra Free，muse-spark-1.3-contributor-free 经常出现 парсинг 然后就停止的问题。”

注意那个俄语”парсинг”（parsing）——这是我手滑打出来的，但场景很真实：模型在解析流式响应时频繁中途停止。看 agent.log 里的调用记录：

一个正常的工具调用轮次输出几百到几千字，这个模型一轮给了 7 个字就结束了，finish_reason=stop（它自己认为说完了）。对于 Agent 来说这是致命的——不是报错，是”礼貌地装死”，Agent 框架不会认为这是异常，只会拿到一段残缺的输出继续往下走，错误会在下游才暴露。

这个体验反过来给了我一个判断标准，后面选模型全靠它：

免费模型的”速度”和”价格”都不重要，重要的是长输出的稳定性。 Agent 的负载是”几十次工具调用 × 长上下文”，一个会在 2000 token 处随机截断的模型，比慢一倍但完整输出的模型贵得多——贵在你的返工时间上。

2. 核心方法 — 四款免费模型分四档路由

2.1 选模型：四款，各有各的坑

我最终路由层里的 4 款模型：

档位 模型 渠道 特点
c0/c1（复杂任务） nemotron-3-ultra-free opencode zen 550B MoE，免费渠道里上下文最长最稳的一个，实测能跑 19 万 token 的长会话
c2/c3（简单任务兜底） agnes-3.0-flash 自建 API Hub 响应快，适合路由、摘要、分类这类短输出任务
备选 nvidia/nemotron-3-ultra-550b-a55b:free OpenRouter 同一模型在 OpenRouter 上的免费端，zen 被限流时的备份通道
已弃用 muse-spark-1.3-contributor-free opencode zen 就是上面那个 7 字元凶，弃用原因：长输出截断

一个很反直觉的发现：同一模型在不同网关上的”模型 ID”不一样。Nemotron 3 Ultra 在 OpenRouter 上叫 nvidia/nemotron-3-ultra-550b-a55b:free（厂商/型号/权重:免费标记），但 zen 网关上叫 nemotron-3-ultra-free。配错 ID 的症状不是 404，而是网关给你路由到一个你意料之外的模型上——白嫖变自费那一刻才会发现账单不对。

几个设计取舍：

  • 档位判断是确定性的，不是 LLM 判断的。 路由依据是本次请求的特征（上下文长度、工具数、是否含代码），一条规则算出来，零 token 开销、零延迟、结果可复现。这一点我们后来沉淀成了一条通用规律：LLM 短输出不稳定时，确定性方案当主力，LLM 只做加分项——把路由这种”分类”任务交给 LLM，你会得到 10 次里 9 次正确但第 10 次离谱的行为，且无法复现。
  • fallback 是从低往高档位降，不是往上跳。 fallback_order: [c3, c2, c1, c0] 的意思是：请求本来的档位失败了，依次试更低成本的档位。复杂任务失败时宁可换模型也不换能力等级——因为”失败”多半是网关侧问题（限流、超时），换同档的其他渠道比降级重跑更划算。
  • hold 机制避免档位抖动。 同一个会话 10 分钟内、5 轮内档位不重算。否则每轮请求的特征稍有变化就在 c0/c1 之间跳，prompt cache 全部失效。

2.3 效果：缓存命中率和长会话都能撑住

换成 nemotron-3-ultra 之后，实测日志（9 月 16 早上的会话）：

三个点：

  1. 19 万 token 的长会话能正常跑完，工具调用走到 77 轮没崩。这是免费模型最容易被低估的能力——大多数”免费档”上下文给得保守（8K~32K），跑多轮 Agent 根本不够。
  2. 缓存命中率 94~96%。zen 网关有 prompt cache，档位稳定（hold 机制）是命中率高的前提。命中了的话，20 万 token 的输入按”近乎零成本”计价——虽然它本来就是免费的，但高命中率意味着延迟低，20 万 token 的续轮 4~5 秒就出结果。
  3. 偶尔有 23.7s 的慢轮次。免费网关的冷启动和限流没法避免，fallback_order 就是为这种时刻准备的：c0 慢了/挂了，自动切 c1（同模型 OpenRouter 通道）。

2.4 为什么敢全走免费档

不是免费就没有代价。真实代价是：

  • 限流窗口不透明。免费档的 RPM/TPM 限制经常不写在文档里，被限了才知道，只能靠 fallback 兜。
  • 模型说下架就下架。muse-spark 从上线到我弃用，满打满算不到 48 小时。所以路由配置里每个模型都是独立 provider 条目，弃用时改配置一行，不用动代码。
  • 输出质量波动。同模型同 prompt，zen 和 OpenRouter 两条通道的回复风格偶有差异。对对话型 Agent 无感，对需要精确格式解析的输出（比如让 LLM 输出 JSON 给下游脚本）要自己加校验。

我的策略是把免费模型分成两类用法：“大脑”类（长推理、长会话）给 nemotron 这种免费里能打的，“手脚”类（路由、摘要、cron 里大量的格式化任务）全部下沉到 agnes flash 这种响应型模型。后者量大但单次便宜到无所谓质量波动，前者量少但对稳定性极其敏感。

3. 踩坑记录 — 三个反直觉的坑

坑一：免费模型截断不报错，只”提前 stop”。
muse-spark 的故障模式是 finish_reason=stop 但输出只有 7 个字。任何”看返回码判断失败”的重试逻辑都抓不到它。我的排查手段是直接在 agent.log 里 grep response_len=，短于阈值的结束轮次就是嫌疑对象。选免费模型先跑 10 轮长输出回归，别只看 demo。

坑二：同一个模型，网关 ID 不一样。
zen 的 nemotron-3-ultra-free 和 OpenRouter 的 nvidia/nemotron-3-ultra-550b-a55b:free 是同一个 550B MoE，但配置里必须各写各的 ID。我一开始图省事两条通道填了同一个 ID，zen 那条通道直接 400。

坑三：把路由交给 LLM 本身是负优化。
最早我试过让一个小模型先看一眼用户请求、输出一个”复杂度评级”再决定路由。10 次里 1 次把简单任务评成复杂档，2 次反过来，且每次行为不同。换成确定性规则后问题消失。规律总结：路由、分档、重试预算这类”分类决策”用代码，生成才用 LLM。

边界：什么情况下别学这套。
如果你的 Agent 负载里有对延迟敏感的实时场景（比如语音助手、秒级客服），免费档的限流和冷启动会让 P95 延迟很难看，这套方案不适用——花小钱用稳定付费档更划算。我这套能成立，前提是所有负载都是异步的（cron 任务、定时简报、批量分析），晚 30 秒没有任何业务影响。

4. 总结

项 值
月 LLM 成本 0 元（4 款免费模型）
路由配置量 30 行 YAML，改 1 行即可换模型/弃用模型
最长稳定会话 196K token 输入，77 轮工具调用
prompt cache 命中 94~96%（档位 hold 是前提）
关键兜底 双通道 fallback（zen → OpenRouter）

一句话 takeaway：免费档的正确打开方式不是”找个免费模型换上”，而是”把免费模型当资源池管理”——按稳定性分档、按成本兜底、确定性路由、随时可弃用可替换。
