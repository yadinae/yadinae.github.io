LLM 把思考过程当正文发表——一道契约门禁如何终结"清洗型"防脏文

发表于2026-09-19|更新于2026-09-30|AI 工程实践

一句话摘要：推理模型的思考段泄漏进正文，靠正则清洗永远追不上——把防御点从”事后清洗”挪到”事前契约”，脏文进不了发布口。

1. 缘起 — 一篇被我手动删掉的脏文

我的雪球自动发帖管线跑了三个月，每天定时出稿。9 月 18 日那天，个股分析环节发出去一篇文章——正文 80% 是 LLM 的思考独白，”让我们分析原文””规划各部分内容””（字数约 180 字）”这种话赫然出现在给读者看的文章里。我删掉了它。

删完我问了自己一个问题：这条管线明明已经跑了这么久、加了那么多清洗规则，为什么还会有这种事？

查完根因，我发现这不是一组零散 bug，而是一个架构性缺陷。今天把整个故障链和修复过程写出来，因为我估计你迟早也会撞上一模一样的墙。

2. 故障链复盘 — 四层防线全在”事后”

先还原 9 月 18 日那天发生了什么。故障是三层原因叠加的结果：

第一层：数据源 name 回显成代码。 东财 API 的 name 字段返回了 "002631" 而不是”德尔未来”，只有 quote.name 里才有真实名称。LLM 拿到带代码名的数据，标题就变成了”股票代码：002631（但用户没有给出股票名称……”——这句话本身就透着一股思考味。

第二层：LLM 客户端的兜底代码成了事故通道。 这是最反直觉的一条。我的 call_llm 里有一行：

这行代码当初是为”推理模型把 token 全花在思考上、正文为空”的场景写的。但它没有区分两件事：思考段和正文是两种东西。当 FreeLLMAPI 自动路由到推理模型、思考耗光所有 token 时，整段思考独白被当文章正文灌进管线——这是脏文的直接来源。

第三层：正则清洗在打地鼠。 管线里有一个 _clean_thinking_leak，用正则匹配已知思考段形式：”首先，……”、”让我检查……”、”现在我需要……”。9 月 17 日就踩过一次思考段泄漏，当时加了一批模式；9 月 18 日 LLM 换了种说法——“原文是……现在，规划各部分……”——新变体不在正则库里，清洗直接失效。

第四层：评审是软门禁。 最后还有一道 LLM 评审，打 1-10 分。结果它打 1.0 分的同时返回 pass=true——自相矛盾也放行。

四层全在”事后”：泄漏发生之后清洗、清洗之后评审、评审之后发布。而 LLM 的思考独白是开放集——正则只能拦住你见过的变体。这就是为什么管线越修越长、越修越脏。

3. 修复 — 把防御点上移到源头和契约

真正的修复只有两条，其余都是配套。

3.1 源头斩断：思考段永远不回退成正文

一行兜底代码换成了显式失败。思考独白从源头上失去进入正文的通道。

3.2 契约硬门禁：用有限集合拒绝开放集合

发布前加了一道结构契约校验，全部是确定性规则，不依赖 LLM：

关键思想：契约是有限集合，LLM 再怎么变体也过不了这道关。”无 ## 标题”这件事对思考独白是恒真的——你不需要枚举所有思考段说法，只需要一个正常文章必然满足、脏文必然不满足的结构属性。

3.3 配套三件套

  • 批量降级：generate_all 里单只股票契约失败 → 跳过继续下一只，不再让 1 只脏文阻塞全天批次；
  • name 回退链：采集侧 name 为空、等于代码、或纯数字时，一律用 quote.name 覆盖，快照落盘即正确；
  • 评审低分门禁：LLM 评审 score < 7 触发修订循环，不再无条件 pass=true。

3.4 验证结果

样本 结果
002631 脏文（事故当天留存） 契约校验 ❌ 拒发 ✓
603268 干净正文 契约校验 ✅ 放行 ✓
全链路 dry-run（中闽能源 600163） 2213 字、结构正常、exit=0 ✓

最坏情况从”发出去被你手动删掉”变成”当天跳过这只股票”。

4. 踩坑记录 — 修复路上的三个小坑

  1. 正则清洗的静默自伤：清洗模式里一条 在2026年 的 pattern 漏了结尾 \n，删行逻辑把整段”行情回顾”连内容一起删了，小节变空。正则库每加一条都要用真实脏样本回归一遍。
  2. 标题截断落在括号里：标题超 50 字被截断后变成”（但没有给出股票名称…”，截点回退到开括号前才自然。API 限制（50 字）+ 品牌前缀（[雅风个股] |）要把余量算清楚。
  3. 摘要字段是独立战线：正文洗干净了，但卡片的 description 取自正文首段——事故当天的首段是脏的，摘要照样带”我们被要求修订一篇雪球文章…”。修复后新草稿不再复现，但已发布的要手动调编辑接口刷。

5. 总结

这次事故教会我的一句话：

对开放集合的输出（LLM 的独白、幻觉、变体），”清洗型”防御注定是打地鼠；要防住它，得用”契约型”防御——找到正常输出必然满足的有限结构集合，把拒绝做成确定性判断。

三条可迁移的行动建议：

  1. 检查你的 LLM 客户端里有没有 if not content: fallback 这种兜底——它是思考段/错误内容进入正文的暗道；
  2. 在”发布”这个不可逆动作前加一道纯代码结构契约，失败就拒，不要用 LLM 评审做最后防线；
  3. 批量管线里单条失败要降级跳过，别让一条脏数据阻塞整批。
