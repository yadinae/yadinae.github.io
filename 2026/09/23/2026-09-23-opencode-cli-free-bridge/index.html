免费 LLM 拒了我的 API 调用，我把官方 CLI 包成了 OpenAI 服务

发表于2026-09-23|更新于2026-10-07|技术实践

摘要：免费大模型的口子越来越多，但免费档的”使用条款”往往藏在行为里而不是文档里。这篇文章记录我 9 月 22 日踩的三个坑——免费网关整账户 429、免费层拒绝一切 HTTP 直连、部署时 Python 版本不匹配——最后怎么用 190 行 Python 把官方 CLI 包成 OpenAI 兼容服务，以及一个让我反悔过一次的架构选择。

1. 缘起 — 免费池一夜之间打满了

上一篇《我的 Agent 现在 0 花费跑 LLM》里，我把 4 款免费模型分档路由，主力大脑是 nemotron 走 zen 网关。9 月 22 日，两个变化同时发生：

  1. mimo-v2.5 全系官方强制下线（9 月 10 日就公告了，到我切完才 11 天）——免费模型的下线周期以天计，路由表里的每一格都要当成随时会失效的资源来管理。
  2. zen/go 免费池整账户预算超限，开始全局 429。

当时的目标是让 6 个 bot 和 2 个定时任务（cron）切到 mimo-v2.6-flash 免费档续命。直连官方的 api.xiaomimimo.com 要等 9 月 27 日配额切换，中间这几天需要一个能打的免费池。

我第一反应是最短路径：zen 上有个 mimo-v2.6 免费通道，配进 provider 表就行。

2. 核心方法 — 190 行桥，把 CLI 变成 OpenAI 端点

2.1 第一个坑：免费层拒一切 HTTP 直连

配置推上去，第一次调用就返回 401，换 token 也 401。折腾了一下午抓请求包对比，发现 zen 免费档的校验不是”有没有 token”，而是**”你是不是从 OpenCode 官方客户端发出的请求”**——9 月 22 日实测，任何用普通 HTTP 客户端模拟的调用（包括带上完整 header 的）全被拒，只有官方 OpenCode CLI 的 headless 调用（opencode run）能通过。

这类指纹校验在免费档很常见，但它有个隐蔽特点：文档里不会写，错误码和鉴权失败完全一样，你从 401 根本推不出”换个 UA 试试”这条路。唯一出路是走官方 CLI。

2.2 架构选择：桥一层，不再叠一层

确认只能走 CLI 之后，我做了个当时让我反悔过一次的架构取舍。

第一版方案是叠三层：agent → OpenLLM 网关 → FreeLLMAPI 本地 550b 缓存 → opencode 免费池。本地 550b 缓存负责高频短问答，miss 了再落到 opencode 免费池。跑起来发现每多一层，故障面就多一个：网关挂了不知道是谁挂的，排查成本按层数翻倍。

跑通之后，6 个 bot profile（coder / critic / edu / research / stock / writer）的主模型 + 2 个定时任务（盘前/盘后漏斗扫描）全部走这个桥，0 花费。

3. 踩坑记录 — 一个我至今没原谅自己的坑

坑：systemd 用了系统的 Python 3.6，所有请求 502。

桥写完部署，systemd 拉起来就疯狂刷错误，日志里反复出现同一句：

我盯着这行日志看了十分钟——capture_output 明明是合法参数，而且本地跑得好好的。直到我注意到错误发生在 subprocess.run 的初始化路径上，才反应过来：

/usr/bin/python3 在这台机器上是 3.6.8，而 capture_output 关键字参数是 3.7 才加的。本地测试我走的是 venv 里的 Python 3.11，systemd 拉的是系统自带版本。

修复：ExecStart 指向 Python 3.7+，或者更彻底——把 subprocess.run(capture_output=True) 换成 3.6 也能跑的 subprocess.run(..., stdout=subprocess.PIPE, stderr=subprocess.PIPE, universal_newlines=True)。

这个坑的价值在于它的隐蔽性：错误不在你的代码里，在你的部署环境里。代码逻辑全对，测试全过，一上生产全挂，而且挂出来的错误信息看起来完全不相干。凡是用 systemd 托管 Python 服务，起完第一件事是 journalctl -u xxx | grep Python 确认解释器版本，别只确认进程活着。

边界：什么时候别做这种桥。

如果你的负载是高并发的（多用户同时调、QPS 上去了），单进程 + 每请求一个子进程的模式撑不住，直接上付费 API。这套方案成立的三个前提，和上一篇一样：负载异步、对延迟不敏感、量小到免费配额够用。

4. 总结

项 值
桥代码量 ~190 行 Python + 17 行 systemd unit
agent 侧改动 provider 表加 4 行 YAML，零代码改动
覆盖负载 6 个 bot profile 主模型 + 2 个定时任务，0 花费
日配额打满时 桥报 5xx，fallback 链自动接管，业务无感
最大坑 系统 Python 3.6 缺 capture_output，所有请求 502

两条可以带走的规律：

  1. 免费档的校验常在行为里不在文档里。 401/403 时先怀疑”它是不是在校验客户端指纹”，把官方 CLI/SDK 通道作为最后退路。
  2. 桥接一层够了，别叠两层。 我第一版叠了三跳（LLM 网关 + 缓存层 + CLI），故障面翻倍、延迟叠加，砍到单桥之后稳定了。调用链每多一层，就要多背一份”它为什么挂了”的排查成本。
