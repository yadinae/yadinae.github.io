我把 AI Agent 的技能库从臃肿精简到锋利——Profile 优化实战

发表于2026-09-09|更新于2026-09-11|技术实践

71 个全局技能、6 个 Profile、每个 Profile 塞了十几个不相关的 Skill——我的 AI Agent 团队看起来很”全能”，实际上每个 Bot 都在处理自己不擅长的事。这篇文章记录我怎么用 Botmaker 方法论，把技能库从臃肿精简到锋利，让每个 Agent 真正专注于自己的领域。

1. 缘起：一个万能 Bot 的「技能虚胖」问题

我的 Hermes Agent 有 6 个 Profile：stock（股票分析）、edu（教育）、coder（代码）、critic（评审）、writer（写作）、research（调研）。一开始，我给每个 Profile 塞了尽可能多的技能——毕竟”技能越多，能力越强”嘛。

结果适得其反。

问题 1：上下文污染。 stock Profile 要分析一只股票，但系统提示里加载了 creative、email、media 这些跟投资完全无关的技能。Agent 的注意力被分散，回复质量下降。更隐蔽的是，有些技能的描述里包含特定的指令模式（比如”使用表格展示”、”添加 emoji”），会微妙地影响 Agent 在不相关场景下的输出风格。

问题 2：身份漂移。 edu Profile 本应专注教案生成，但加载了 social-media 和 note-taking 技能后，它偶尔会”串岗”去写社交媒体文案。这在单 Agent 场景下无伤大雅，但在多 Agent 流水线里是灾难——当你把任务委派给 @edu 时，你不希望它返回一份微博文案。

问题 3：Token 浪费。 每个技能的 SKILL.md 描述会注入系统提示。71 个技能即使每个只占200 token，总量也有14K token——每一轮对话都在为不相关的能力买单。而且这些技能描述还挤占了真正重要的内容空间：SOUL.md 的身份定义、FLEET.md 的全局状态、工具的使用指南。

问题 4：维护噩梦。 当一个技能需要更新时，你要在所有引用它的 Profile 里同步修改。一旦漏改一处，不同 Profile 对同一技能的理解就会产生分歧——这是”多处真相”问题的经典表现。

我需要的不是”什么都会的全能选手”，而是”在自己的领域里无可替代的专家”。

2. 核心方法：Botmaker 方法论 + 「赢得的技能」原则

2.1 Botmaker 方法论：身份=职能（反伪装）

Botmaker 的核心观点：Bot 的身份就是它的职能，不是它的”人设”。

我据此重写了每个 Profile 的 SOUL.md。以 stock 为例：

关键转变：从”你能做什么”到”你不做什么”。显式排除边界，比隐式包含更有效。这借鉴了软件设计中的”防御性编程”思想——你不是假设输入一定正确，而是主动检查并拒绝非法输入。

2.2 「赢得的技能」原则：技能是挣来的，不是分配的

传统做法是给每个 Profile”分配”技能——“stock 需要分析能力，所以给它 stock-mcp-optimization；还需要写报告，所以给它 creative”。这种思路的问题是：分配基于想象，不是基于事实。

Botmaker 反过来：每个技能必须通过”赢得”才能加入 Profile。

判断标准（三个问题）：

  1. 使用频率：这个技能在过去 30 天内被该 Profile 实际调用过？
  2. 职能匹配：调用时产出的结果符合该 Profile 的核心职能？
  3. 独立性：去掉这个技能后，该 Profile 的核心任务是否受影响？

三个问题中有一个答”否”，就移除。

实操中的具体判断：

技能 Profile 30天调用 职能匹配 去除影响 决定
stock-mcp-optimization stock ✅ 每天 ✅ 行情分析 🔴 核心 保留
planning-with-files stock ✅ 偶发 ✅ 规划分析 🟡 可替代 保留
creative stock ❌ 从未 ❌ 不相关 🟢 无影响 移除
email stock ❌ 从未 ❌ 不相关 🟢 无影响 移除
cangjie-skill edu ✅ 每周 ✅ 内容蒸馏 🟡 重要 保留

2.3 FLEET.md：单一事实来源

我把所有 Profile 的状态、技能、调度信息汇总到一个文件 FLEET.md，放在 Hermes 根目录：

为什么需要 FLEET.md？ 因为当配置分散在6个 Profile 目录里时，你永远不知道”谁有什么、谁该有什么”。改了一个 Profile 的技能列表，其他 Profile 不会自动感知。FLEET.md 让全局状态一目了然——改之前先看一眼，改之后再看一眼，确认没有遗漏。

3. 踩坑记录：精简过程中的真实教训

坑 1：Curator 管理的技能不让删

Hermes 有一个”Curator”自动管理机制，会自动给技能打补丁、优化描述。当我试图删除一个 Curator 管理的技能时：

根因：Curator 认为这个技能被其他技能引用（通过 references/ 目录），所以拒绝删除。

解法：先确认技能是 created_by=None（用户自建）还是 Curator 管理的。用户自建的技能可以直接删；Curator 管理的需要先解除引用关系——删除 references/ 目录里的链接，或者把引用改为指向全局技能。

坑 2：技能描述60字符硬限制

尝试创建一个 botmaker-methodology 技能时，连续6次被拒：

根因：Hermes 的技能描述有60字符的硬限制——因为描述要注入系统提示的”技能投影”区域，太长会挤占其他内容的空间。系统提示的总 token 预算是固定的，每个技能多占一点，所有技能加起来就是一大块。

解法：精简到一句话，用最短的表达说清楚技能的用途。最终版本：

14个字符，干净利落。

坑 3：通用技能该放哪里？

planning-with-files、wiki-search、productivity 这些技能多个 Profile 都需要。到底放全局还是每个 Profile 都复制一份？

原则：

  • 小型通用（如 planning-with-files，SKILL.md < 2KB）→ 放在需要的 Profile 里，按需加载
  • 大型通用（如 creative、research，SKILL.md > 5KB）→ 只放在最匹配的 Profile
  • 绝不复制：同一技能不要在多个 Profile 里维护多份。一旦复制，更新时就要同步多处——这是”多处真相”问题的根源

最终结构：stock 只保留4个核心技能（planning-with-files、productivity、stock-mcp-optimization、wiki-search），完全不加载跟投资无关的能力。

坑 4：Multiplex 模式下的技能隔离

飞书 Multiplex Bot 模式下，多个 Profile 共享一个飞书 Bot。用户发一条消息，Hermes 根据内容路由到最合适的 Profile。如果某个 Profile 加载了不相关的技能，消息路由到它时会产出不相关的回复。

解法：在 config.yaml 中限制参与 Multiplex 的 Profile：

只有 stock 和 research 参与飞书 Multiplex，其他 Profile（如 edu、writer）不接收飞书消息。这样即使 edu 加载了13个技能，也不会在飞书群里”串岗”。

4. 精简结果：从「全能选手」到「领域专家」

优化后的6个 Profile 技能分布：

Profile 技能数 核心技能 职能
stock 4 stock-mcp-optimization, planning-with-files 行情分析、投资决策
edu 13 cangjie-skill, deeptutor-research, ruankao-* 教案生成、学员辅导
coder 5 software-development, codebase-modification-discipline 代码开发
critic 12 autonomous-ai-agents, codebase-modification-discipline 质量评审
writer 12 creative, marketing, social-media 内容创作
research 10 research, creative, web 资料调研

关键数据：

  • 全局技能：71 个（含系统内置）
  • Profile 专属技能：56 个（总计，分布在6个 Profile）
  • 每个 Profile 平均技能数：9.3 个
  • stock Profile 最精简：仅4个技能（全系统最少）

效果对比

指标 优化前 优化后
stock 平均回复延迟 高（技能搜索耗时） 低（4个技能，精准匹配）
跨 Profile 串岗频率 偶发（每周1-2次） 近零
每轮 Token 消耗 ~14K（全局技能注入） ~4K（仅相关技能）
Profile 维护成本 高（多处同步） 低（FLEET.md 单一事实来源）
新 Profile 创建时间 ~30分钟（选技能纠结） ~5分钟（按职能选核心技能）

5. 总结：一句话 Takeaway

技能是挣来的，不是分配的。每个 Agent 应该只拥有它在过去30天内证明自己需要的能力。

行动建议：

  1. 审计现有技能：列出每个 Profile 的技能，逐个问”过去30天用过吗？”
  2. 显式排除边界：在 SOUL.md 中写清楚”你不做什么”，比写”你能做什么”更有效
  3. 单一事实来源：用一个 FLEET.md 文件管理所有 Profile 的全局状态
  4. 限制 Multiplex 参与：只让核心 Profile 参与飞书 Multiplex，避免串岗
  5. 技能描述≤60字符：Hermes 的硬限制，提前规划好每个技能的一句话描述
  6. 不要复制技能：同一技能只维护一份，按需分配到需要的 Profile
