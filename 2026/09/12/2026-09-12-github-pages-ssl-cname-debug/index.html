GitHub Pages 博客挂了——从 Cloudflare 526 反推 CNAME 丢失，一条完整排障记录

博客突然打不开，Cloudflare 报 526 SSL 握手失败。我以为是证书过期了，折腾了一晚上，最后发现真凶是一个一行文本的 CNAME 文件丢了。这篇文章完整记录这次排障——包括我走过的弯路、真正起作用的排查顺序，以及给”静态博客 + 自定义域名 + Cloudflare”这套组合的避坑清单。

2.2 我踩的第一个坑：把”现象”当”原因”

526 只描述了一件事：Cloudflare 连源站时 SSL 失败。它既可能是证书问题，也可能是 CNAME 丢失导致 GitHub Pages 根本没把这个域名认作自己的站点（此时 Pages 返回的是默认的 github.io 证书，跟 Cloudflare 拿到的不匹配）。

我花了一小时在搜索”Cloudflare 526 GitHub Pages”的结果里打转，那些答案全是”删 CNAME 重签”的方案。没有一条提到过先检查 Pages 仓库里 CNAME 还在不在——因为 CNAME 文件丢失是自己仓库的状态，Cloudflare 那侧的错误日志不会告诉你。

3. 踩坑记录 — 反例与边界

3.1 什么时候”删 CNAME 重签”方案是对的？

网上流传的 temp: remove CNAME 操作，适用场景是：CNAME 文件一直存在且内容正确，但 Cloudflare 的 SSL 模式（Full/Full Strict）与 GitHub Pages 自动签发的证书不匹配，导致 526。此时删 CNAME → 触发重新签发 → 恢复，确实有效。

3.2 GitHub 文档里其实有明确说法，但我忽略了

GitHub Pages 官方文档说得很直白：CNAME 文件放在部署产物仓库的根目录（不是分支名子目录下），Pages 就识别为该域名的站点。Hexo 用户如果不用 hexo generate 直接把 public/ 推上去，就必须让 source/CNAME 跟着构建流程走一遍。文档地址：

3.3 一个反直觉的点

我最初以为 Cloudflare 那侧 526 是”证书过期”，因为 Cloudflare 的 5xx 错误页就是这么提示的。但 5xx 只说明”源站拒绝了连接”，不说明”拒绝的原因”。所有”源站 SSL 问题”都可能表现成 526/521/522/525——SSL 握手失败是 525/526，源站不可达是 522，源站超时是 524。看到 5xx 先做分诊（类比医院急诊：先分内外伤，再进科室），而不是直接跳去 SSL 专科。
