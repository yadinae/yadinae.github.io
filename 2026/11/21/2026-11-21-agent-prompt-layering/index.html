当 AGENTS.md、CLAUDE.md 和 Skill 打起来了——AI Agent 指令分层实战

发表于2026-11-21|更新于2026-11-28|技术实战

一句话摘要：本文从三个真实翻车案例出发，讲清楚 AGENTS.md、CLAUDE.md、SKILL.md 这三层指令的优先级规则、常见冲突模式，以及一套「可验证」的分层设计方法——让 agent 不再在互相矛盾的指令里随机选一边。

1. 缘起 — 一次「你说东我说西」的生产事故

2026 年 9 月，我把 Hermes 的技能库从 255 个精简到 190 个。剪完之后清爽了，但两周后开始出怪事：

有一次写飞书格式化报告，系统提示里明明有「禁止 HTML 标签」的规则（来自全局 AGENTS.md），但 feishu-format 这个 skill 的输出却在某些字段里夹带了 <br>——因为那个 skill 里的 instructions 是三个月前写的，当时还没这条规则。

还有一次，stock profile 该按 botmaker-methodology 的要求只做数据输出，但它突然开始给每行数据加 emoji 图标——原因是某个不相关的 skill 描述了 emoji 用法，被加载进来了。

我意识到：agent 不是一个「读一条指令就执行」的简单机器，它是一个同时接收 N 条可能互相矛盾的指令的复杂系统。

更可怕的是：这些矛盾不会报错，会静默地选一边走下去，而你完全不知道它选了哪条。

2. 核心框架 — 四层指令栈

最近 viral pipeline 抓到一个热门话题：「When AGENTS.md, CLAUDE.md, and a Skill Disagree, Which One Wins?」——正好戳中我们这几周踩过的所有坑。

2.1 四层指令栈

AgentPatterns.ai 的总结很精辟：越靠近具体任务的层优先级越高（用户消息 > Skill > 项目指令 > 系统提示）。但这只是趋势性规则，不是强制保证——矛盾出现时，模型会在两句话之间随机摇摆，没有任何警告。

2.2 为什么这不只是理论问题？

因为我们用的是多 profile 架构：

Profile 职责 特有指令来源
stock 股票分析 FLEET.md 角色定义 + prism-* 系列技能
edu 教案生成 botmaker-methodology + cangjie-skill
critic 质量评审 QGS 三层架构 + 评审规则集
writer 内容创作 feishu-format + blog-publisher
research 资料调研 multi-search-engine + weixinpay
default 主会话 以上全部 + SOUL.md + MEMORY.md

每个 profile 都会加载自己的 skills，而 skills 内部又可能有指令。同一个规则在不同 context 下含义不同，这才是最难 debug 的地方。

3. 三个真实翻车案例

翻车 #1：Skill 里的旧规则悄悄复活

场景：2026-11-18 那次飞书 App 迁移排查。

根因：我们在迁移飞书应用时，把白名单校验逻辑改了，但 feishu-format 技能的描述里还有一行：

「发出支付确认链接或绑定链接后立即结束本轮，不轮询」

这一行的语义和我们改后的 gateway 逻辑产生了微妙冲突——模型在某几轮里优先读了这条旧 skill，导致消息发送流程跑偏。

教训：Skill 的 description 字段虽然理论上只在匹配时被注入，但只要 agent 读过它就进了 context。一个三个月前的描述，依然能影响今天的决策。

翻车 #2：Emoji 风格溢出

场景：2026-11-16 的每周灵感投喂 cron。

根因：FeishuMessageSender 工具的输出模板里要求用 ✅ ❌ ⚠️ 🟢 🟡 🔴 标记状态，这是正确的。但与此同时，prism-* 系列分析技能的 description 里也提到了 emoji 使用方式。两个 source 都在告诉 agent「要用 emoji 标记」，但频率和样式不一致——结果报告要么 emoji 太多显得花哨，要么格式不统一。

教训：同一行为模式（用 emoji 标记）不应出现在多个层级中。「一处定义，多处引用」比「多处定义自行解释」安全得多。

翻车 #3：系统提示的 Compliance Ceiling

场景：多次 cron job 运行中，SOUL.md 里的硬约束有时会被忽略。

根因：AgentPatterns.ai 的研究指出，指令遵循率随 stack depth 递减——Beyond 大约 10 条关键规则之后，低优先级规则会被 silent drop。我们的 SOUL.md 加上各 profile 的 instruction 加起来超过 40 条——这意味着很多软约束根本不在 model 的有效注意力范围内。

教训：与其写 40 条「应该遵守」的规则，不如把最重要的 3-5 条放到最前面并重复声明。

4. 方法论 — 可验证的分层设计

经过这几个月的试错，我总结了以下实践：

4.1 规则去重审计（每月一次）

每次剪枝或新增 skill 后，对全量描述做一次 grep 审计：

发现多处同义描述 → 删掉多余的，只保留一份权威来源。

4.2 关键约束三层锚定法

对于真正重要的规则（如「QGS gate 未通过不推送」），不止写一遍，而是锚定到三层：

层 写入位置 写法
System SOUL.md / config 一句硬约束：”Gate 未通过 = 零输出”
Skill qgs-auto-gate/SKILL.md 详细流程和退出条件
Cron jobs.json 明确的 failure_deliver 路径

这样即使某一层被静默 drop，其他两层还能兜住。

4.3 Profile 隔离严格化

每个 profile 只加载领域专属 skill，不放通用类大 skill：

实测效果：default profile 从 190 skills 减到核心 20+ 后，输出一致性显著提升，context 浪费减少约 70%。

4.4 AGENTS.md vs SKILL.md 的分工边界

放入 AGENTS.md（始终生效） 放入 SKILL.md（按需加载）
身份定义、hard constraints 单任务工作流步骤
跨 profile 通用规则 特定领域的专业知识
安全红线（不输出 [SILENT] 等） 动态生成的内容规范
协作接口协议 临时性的 prompt 优化

原则：如果一条规则在任何场景下都必须遵守，放 AGENTS.md；如果只在特定任务下有效，放 SKILL.md。

5. 踩坑记录

5.1 子代理会丢失父级指令

当 parent agent 调用 subagent（比如 @coder 被 @research 调度）时，subagent 不继承 parent 的 project instructions。除非显式传递，否则 subagent 的上下文里完全没有 AGENTS.md 的内容。

我们踩过的一例：@critic 评审文章时没读到 feishu-format 的 Markdown 表格规则，输出了 +---+ 文本表格而非管道表格——然后 QGS gate 因为「破坏 Markdown 渲染」拒绝通过。修法是：在 @critic 的任务 prompt 里显式注入 feishu-format 的关键规则。

5.2 位置偏差（Positional Bias）

Purpura et al. (2026) 的研究证实：位于 prompt 靠后位置的规则更容易被遵循。 所以：

  • 不要把所有规则堆在文件中间
  • 把最重要的规则放在开头（primacy effect）和结尾（recency effect）各来一次
  • 不要在长文档后面追加新规则——它们大概率不会被读到

5.3 Compliance Ceiling 不可违反

10 条关键规则用平铺列表的方式，比 40 条分散在四个 layer 的方式效果更好。与其增加 rule 数量，不如提高 rule 的可信度（credibility）——通过 repeated enforcement 而不是 repeated listing。

6. 总结

三条 takeaway：

  1. 矛盾静默发生：层与层之间的冲突不会报错，model 随机选一边走下去。你必须做去重审计才能发现隐患。
  2. 关键规则要锚定三层：系统层 + skill 层 + runtime 层各写一遍，降低任一 silient drop 的影响。
  3. Profile 隔离是最好的防污染手段：每个 profile 只加载必要的 skill，context 预算留给真正重要的内容。

最后送一句我在实际运维中反复验证的话：

你无法指望 agent 在所有情况下都做出正确选择。你能做的是让错误的选择代价足够低。

— 龙天涯
