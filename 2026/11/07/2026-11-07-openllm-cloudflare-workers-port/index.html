我们把 LLM 网关搬到 Cloudflare Workers，编译全过却静默翻车——5 个隐形移植 Bug

发表于2026-11-07|更新于2026-11-18|工程实践

一句话摘要：把一套跑了半年的 Deno LLM 网关搬到 Cloudflare Workers 上，TypeScript 编译 0 错误、esbuild smoke 全过，但上线后一半功能在静默地错——不报错、不崩溃，只是返回”看起来正常但其实是错”的结果。我们拆出了 5 类隐形移植 Bug，都是 serverless 边缘环境特有的。

1. 缘起 — “移植完了”和”真的能用”之间，隔着 5 个隐形炸弹

我们的 OpenLLM 是一个多租户 LLM 网关（OpenAI 兼容 /v1/chat、Ollama 协议、embeddings、transcription 一应俱全），跑了半年的 Deno Deploy。为了更好的边缘分发和国内可访问性，我们决定把它整体搬到 Cloudflare Workers。

这是个 7000+ 行的迁移，按 Batch 分天推进。到 Batch B 时，TypeScript 编译 0 错误、esbuild smoke 26/26 全过——我们以为胜利在望了。

但真正压上去跑真实流量才发现：编译全过 ≠ 功能正确。它不崩、不报错，而是返回”看起来对、其实是错的”结果。这种静默失败比直接报错可怕十倍——因为你在生产环境根本发现不了，直到用户拿着错误结果来问你。

我们最终拆出了 5 类隐形移植 Bug，每一类都值得单独写一篇。下面逐个拆解。

2. 核心方法 — 5 个隐形 Bug 的根因与修法

2.1 模块顶层 new Date() = epoch 0（Workers 全局作用域规则）

症状：Ollama 的 /api/show 永远返回 modified_at: "1970-01-01T00:00:00.000Z"，Ollama UI 显示”55 years ago”。

根因：原代码在模块顶层写了 const CATALOG_MODIFIED_AT = new Date().toISOString()。在 Node/Deno 里这没问题——模块加载时拿到真实时间。但在 Cloudflare Workers，模块顶层代码在 isolate 全局作用域初始化时执行，此时时钟是 epoch 0。Cloudflare 明确禁止模块级副作用（error 10021 类），时间相关的模块级求值全都会得到 1970-01-01。

修复：改成懒初始化——首次使用时才 new Date()：

2.2 哈希算法漂移：FNV 和 SHA-256 各算各的 → 会话静默失效

症状：Ollama 协议的 dashboard-session 分支永远不生效，getSessionUser 永远查不到用户，请求总是走”外部 auto 视图”。

根因：登录/会话存储用的是 d1.hashToken（真 SHA-256），但 Ollama 会话校验用的却是 auth.hashSessionToken——一个同步 FNV 回退实现，算出的 digest 跟 SHA-256 对不上。两个哈希函数在同一个系统里各自为政，getSessionUser(hash(token)) 拿 SHA-256 的 key 去查 FNV 算出的记录，永远查不到，于是静默禁用整条会话分支。

修复：统一成一个来源——Ollama 改用 await hashToken(token)（与 login/chat/models 一致），并加固 auth.hashSessionToken 也改成 async WebCrypto SHA-256，保证任何模块都不会再漂移。

💡 教训：跨模块的加密/哈希函数必须收敛到单一真源，并加一条跨模块一致性断言——编译期测不出来，但这是这类”静默错”的重灾区。

2.3 “PICK ≠ RETRY”：把 fallback 重试语义映射成了单次选择

症状：Ollama 的 /api/chat 和 /api/generate 遇到 stale primary key 直接 401 且不重试；但同样的请求走 /v1/chat 却能成功。

根因：Deno 版的 executeWithFallback() = 选 best provider + 执行 + 失败沿 fallback 链重试。但移植时被”等价”成了单个 routeSignal() + adapter.chat() 调用——而 routeSignal 只负责挑选，不带重试。于是主 key 一挂，整个请求就死了。

修复：Ollama 的 auto/fusion 分支复用 chat.ts 的完整主备循环（routeSignal → adapter.chat → 失败后 routeSignal({ignoreCooldown, forceProvider}) 选下一个 → 重试），并把 collectFallbackProviders 从 chat.ts export 出来共用，让 fallback 顺序只有单一事实来源，不复制第二份链逻辑。

2.4 死代码的数据缺口：transcription 是”从未跑通过”的蓝本移植

症状：/v1/audio/transcriptions 永远返回 'No STT providers available'——哪怕配置了健康的 STT key。

根因：这条路径是 FreeLLMAPI 的移植，在原蓝本里就是死代码，从没真正跑通过。要激活它，光改数据不够，需要 4 处代码修复：

  1. 能力门缺字段：ProviderCapabilities 根本没有 audio.transcription 字段，getSTTCandidates 检查 if (!caps?.audio?.transcription) continue 把每个 key 都 skip 了。加字段并在 Groq/OpenAI 上声明即可（Whisper 兼容）。
  2. 模型名映射缺失：'groq/whisper-large-v3' 被原样传给 Groq（被拒），裸 'whisper-1' 又传到非 OpenAI。加 upstreamModelName() 剥离前缀 + 映射默认 STT 模型。
  3. 二进制 multipart 被当 UTF-8 解：TextDecoder().decode(wholeBuffer) 再 split 再 encode——wav/mp3 不是合法 UTF-8，非法字节被替换成 U+FFFD，每个音频文件都损坏了。改成字节级解析：headers 文本解码、文件字节原样拷贝。
  4. 非 JSON 响应被强制 res.json()：response_format=text 返回纯文本，res.json() 直接抛 503——在转录已经成功后。分支处理：text → {text: raw}。

修完后，真实 6 秒语音样本 json/text/verbose_json/vtt 全部 200，vtt 正确返回 WEBVTT 字幕。

💡 教训：“从蓝本移植”最危险的是蓝本本身就有 bug——你在忠实复刻一个坏实现。移植完成后要用真实端到端请求验证，而不是只测”编译过了”。

2.5 硬编码 expectedDim=0：校验维度把每个真实向量都拒了

症状：embeddings 所有 openai-style 路径（cloudflare/nvidia/openrouter/custom…）全部报 mismatched dimensions (expected 0)。

根因：validateDimensions(data, dimensions, 0) 把 expectedDim 硬编码成 0。当请求没传 dimensions 时，dim = (undefined ?? 0) = 0，于是每一个真实向量都被判定为”维度不匹配”被拒。这是蓝本移植直接带过来的 bug。

修复：没显式请求 dimensions 时，用第一个返回向量的长度作为期望值——校验的是”所有向量互相一致且有限”，而不是跟 0 比：

3. 踩坑记录 — 这 5 个 Bug 背后的 3 条共性

共性 1：编译通过和 smoke 通过，验证的都是”形状”不是”行为”

TSC 0 + esbuild smoke 26/26，验证的是类型和模块边界——它测不出 epoch 0、哈希漂移、binary 损坏这类运行时语义问题。移植服务，编译通过只是起点，必须用真实请求逐个端到端验证每个协议分支。

共性 2：静默失败 > 直接崩溃

这 5 个 bug 没有一个抛异常。epoch 0 正常返回、哈希不对只是查不到、binary 损坏是”文件处理失败”——全都表现为”正常但错”。边缘环境的移植，要刻意写”断言式”验证：不只是 200，还要校验返回内容的正确性（维度、字幕、会话分支是否生效）。

共性 3：移植要”复刻”还是”重写”？——关键边界要重建而不是照抄

executeWithFallback 和 hashSessionToken 这两个 bug，本质是移植时为了”少改”而取了最小等价物，结果丢掉了语义。而 collectFallbackProviders 的共用则说明：重用的单一真源，比复制的第二份实现可靠。移植的哲学应该是一一保留语义，不是一一保留代码形状。

边界：什么时候这套方法不适用？

  • 如果你只是”部署”一个 Worker（不涉及大范围语义移植），这些坑大多不适用。
  • 如果你的原系统本身没有 fallback/哈希这类”行为契约”，就不存在”PICK ≠ RETRY”问题。
  • 但只要你是把一套成熟的 serverless 服务搬到另一家 serverless 平台（Deno→CF、Vercel→CF 同理），”全局作用域副作用””哈希算法漂移””二进制 body 被文本化”这几类坑大概率都会遇到——因为它们的根子在”平台运行时契约差异”，跟具体代码无关。

4. 总结

核心 takeaway：把服务搬到边缘 serverless 平台，最大的敌人不是编译错误，而是**”编译全过、行为全错”的静默失败**。Cloudflare Workers 的全局作用域规则、哈希/加密的跨模块一致性、PICK ≠ RETRY 的语义映射、”蓝本自带死代码”和硬编码校验值，构成了移植路上 5 类最容易踩中的隐形炸弹。

一个可复用的移植清单：

  1. 模块顶层副作用全部懒初始化（时间、随机、IO）
  2. 跨模块哈希/加密收敛到单一真源 + 一致性断言
  3. “选择”和”重试”是两件事，别用一个函数替代另一个
  4. 用真实端到端请求验证协议分支，不止验证编译和 smoke
  5. 校验值别硬编码，从真实数据推导（并保留显式参数优先）

一句话：编译通过是移植的开始，端到端语义验证才是移植的完成。
