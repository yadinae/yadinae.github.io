飞书换 App 后私聊全量静默拒绝 —— open_id 是 app-scoped，拒绝只记 DEBUG，INFO 干净不代表没拦截

发表于2026-11-18|更新于2026-11-18|技术实战

一句话摘要：把 Hermes 的飞书应用从旧 App 切到新 App（MyVela）后，用户私聊完全无响应。开放平台侧逐项核过全部正常（应用已发布、事件订阅 im.message.receive_v1、长连接验证通过、36 项权限齐全），表象像「飞书没推事件」。实测根因：open_id 是 app-scoped，白名单里留的是旧 App 签发的 open_id；拒绝路径只记 logger.debug，INFO 级别日志完全无痕。

1. 缘起 —— 「开放平台全绿、websocket 连着、私聊没反应」

故事发生在 2026-11-11 到 11-12。我们把 Hermes 的飞书 Bot 从旧应用 cli_a9421ef534781bde 迁移到新应用 MyVela（cli_aa7fbdfdd7b89c01）。迁移动作看似标准：

  1. 在开放平台创建新应用、配置事件订阅、发布上线
  2. 更新 .env 里的 FEISHU_APP_ID、FEISHU_APP_SECRET
  3. 重启 Hermes gateway

按理说这应该是分分钟的事。但用户反馈：私聊完全没反应，群聊正常（群聊不走白名单）。

第一反应是查开放平台——应用状态「已发布」、事件订阅 im.message.receive_v1「已启用」、长连接「验证通过」、权限列表 36 项「全勾选」。截图留存、API 逐项核对，表象全绿。

但 gateway.log 里完全没有 Received raw message 记录。这就怪了——websocket 连着，心跳正常，为什么没收到消息？

2. 排查过程 —— 从「飞书没推」到「自己拦了」

2.1 走了多少弯路

尝试方案 耗时 结果
反复查开放平台发布状态、事件订阅、权限 2 小时 逐项截图 + API 核对全部正常，排除
反复重启 gateway 逼重连 4 次重启 11-12 08:12 / 08:16 / 08:54 / 08:55 后依旧无消息，排除
FEISHU_ALLOW_ALL_USERS=true 临时放行 30 秒 一行 env + 重启即恢复；代价：白名单形同虚设
查回新 App 视角的真实 open_id 写回白名单 未执行 正解（见下文）

关键转折点：加上 FEISHU_ALLOW_ALL_USERS=true 后，消息瞬间恢复。这说明飞书确实推了消息，是我们自己在 gateway 里拦截了。

3. 核心根因 —— open_id 是 app-scoped

这是最容易被忽视的一点：飞书的 open_id 是按应用隔离的。

维度 旧 App (cli_a942...) 新 App MyVela (cli_aa7f...)
用户的 open_id ou_b9c84362211cd4a767056b1f5f660d3d ou_0047b9b307a070440ea42a6fbf82ef26
白名单里存的 ou_b9c8436...（旧 App 签发） 同一个旧 open_id（未同步更新）
结果 匹配，放行 不匹配，拦截

同一个飞书用户，在不同应用下的 open_id 完全不同。这是飞书的设计——防止跨应用追踪用户。我们只换了 FEISHU_APP_ID，忘了同步换 FEISHU_ALLOWED_USERS。

4. 踩坑记录 —— 反例、边界与可复用规则

4.1 我掉过的坑

坑 表现 教训
只换 App ID，不换白名单 私聊全量静默拒绝，INFO 日志无痕 FEISHU_APP_ID 变了，必须同步换 FEISHU_ALLOWED_USERS
信「INFO 干净 = 没拦截」 排查 4 小时查开放平台、重启 gateway 拒绝只记 DEBUG，INFO 干净 ≠ 没拒绝
没按「新 App 视角」取真实 open_id 白名单里存的是旧 App 签发的 id，新 App 下无效 必须在新 App 下触发一次消息，从 gateway.log 里拿 origin.open_id

4.2 什么情况下这个方法不适用

  • 群聊场景：群聊消息不走白名单校验，换 App 无感
  • FEISHU_ALLOW_ALL_USERS=true：白名单直接失效，但任何飞书用户都能私聊 Bot（安全风险）
  • 没配白名单（FEISHU_ALLOWED_USERS 为空）：默认全放行，无此问题

4.3 容易混淆的概念

现象 真相 常见误判
websocket 连着、心跳正常 长连接建立 ≠ 消息能进业务逻辑 ❌ 以为飞书没推
开放平台权限/订阅/发布全绿 只管「能不能收到」，不管「收到后怎么处理」 ❌ 以为配置没问题
gateway.log INFO 完全无 Received raw message 被 _admit() 在 DEBUG 里拦截了 ❌ 以为没收到消息
同一用户、不同 App 的 open_id 不同 飞书 open_id 是 app-scoped 设计 ❌ 以为 open_id 是用户全局唯一

6. 遗留风险与多 Profile 注意事项

6.1 当前遗留风险（本次未完全解决）

  • 主 .env 现仍 FEISHU_ALLOW_ALL_USERS=true，白名单仍是旧 App 的 ou_b9c8436...——直接关 ALLOW_ALL 会立刻回到全量静默拒绝
  • 计划中的「查回真实 open_id 写回白名单、关 ALLOW_ALL、重启」未执行

6.2 多 Profile 独立 App ID

Hermes 支持多 profile（coder/critic/edu/research/stock/writer），每个 profile 可以有独立的飞书 App：

Profile 当前 App ID 状态
research cli_a90b5d6d8e395bc9 独立，不受本次影响
stock cli_aab9821acb789bee 独立，不受本次影响
coder/critic/edu/writer 无配置 后续若配飞书，白名单必须按各自 App 重新取

同类错误已是第二次（10-03 已写进 hermes-multi-bot-orchestration 技能仍未防住）。本次已把「app-scoped 校验 + DEBUG-only 拒绝信号」补进 hermes-gateway-management 的「收不到消息」排查清单。

7. 总结 —— 核心结论与一句话 Takeaway

7.1 核心结论

  1. 飞书 open_id 是 app-scoped——换 FEISHU_APP_ID 必须同步换 FEISHU_ALLOWED_USERS，这是物理隔离，绕不开
  2. 拒绝只记 DEBUG，INFO 干净 ≠ 没拒绝——排查「收不到消息」时，先查有没有 Received raw message：有 = 收到没回，没有 = 压根没进来（或被 DEBUG 里拦了）
  3. 临时开 ALLOW_ALL_USERS 是最快的诊断手段——一行 env 能瞬间验证「是飞书没推」还是「自己拦了」

7.2 一句话 Takeaway

换飞书 App，白名单不跟着换 = 私聊全挂；拦截只记 DEBUG，INFO 干净别当真。先开 ALLOW_ALL 验收消息，从日志拿新 open_id，再锁白名单。
