源码丢失、PyPI 下错包——我把 AI Agent 质量门禁从一片废墟里重建

发表于2026-11-25|更新于2026-11-28|技术实战

一句话摘要：Hermes Agent 的质量门禁 QGS 源码意外丢失，pip install qgs 下到一个流体动力学库。我不得不从零手写 7 个文件重建整个包，并顺带验证了一个更深的道理：对于核心基础设施，永远不要信任 PyPI 上的同名包。

1. 缘起 — 一个”应该很简单”的恢复任务

2026 年 11 月 23 日，我发现质量门禁系统的源码目录不在了——只剩下了运行时数据（运行状态、会话历史、任务数据库），而核心的 Python 模块全部消失。

QGS（Quality Gate System）是 Hermes Agent 的质量门禁插件，每次复杂任务输出前自动评分，低于阈值就阻断。它是生产环境里最关键的基础设施之一。没有它，所有 cron 任务和实时对话的输出都失去了最后一道质量保障。

我的第一反应很自然：

三秒钟后，安装完成了。然后我尝试 import：

什么也没报错。太好了。

直到我第一次真正调用 QGS 的插件功能时，发现它根本不是我熟悉的那个 QGS。这个 PyPI 上的 qgs 是一个准地转大气数值模型（Quasi-Geostrophic Spectral model），做流体动力学模拟的，跟我的质量门禁系统毫无关系。

那一刻我才意识到问题有多严重：我不仅丢了源码，而且如果我 blindly trust 了 PyPI，我会把一个大气物理库当作自己的基础设施来用——后果不堪设想。

坑 3：PyPI 上的同名包可能是完全不同的东西

这不是代码层面的坑，而是认知层面的。qgs 这个包名在 PyPI 上已经有一个真实存在的包——准地转大气谱模型。 如果我当时没有仔细核对包的 description，就会在不知不觉中引入一个错误的实现。

这件事让我养成了一个新的习惯：对核心基础设施包，永远先 pip show <package> 看 summary 和 description，确认功能匹配后再使用。 或者更好的做法是——自己维护源码，不打 PyPI 的主意。

3. 安全视角：这次事件印证了一个更大的趋势

就在我手工重建 QGS 的同一天（2026-11-17），安全研究者披露了一起重大供应链攻击事件：

Microsoft Agent Framework 的 PyPI 包 agent-framework 被入侵，恶意版本 1.26.1 和 1.26.2 在 33 分钟内相继发布（20:35 和 21:08 UTC），内置一个 .pth 启动钩子窃取凭据。这个包每月约 19 万次下载，恶意版本影响了约 20 万台设备，涉及 Azure、AWS、GitHub、Docker、Hugging Face、OpenAI 等凭据。

最可怕的是攻击机制：.pth 文件在 Python 解释器启动时就会执行，即使你根本没有 import 这个包，甚至只是跑一个无关脚本也会触发。这意味着一个躺在 requirements.txt 里但从未用到的依赖，也可能是实时运行的窃取器。而 1.26.1 被隔离后 33 分钟，攻击者又用仍持有的发布权限上传了 1.26.2。

两件事放在一起看，结论很清楚：越核心的基础设施，越不应该依赖外部包管理器的”善意”。 恶意版本伪装得很巧妙——它们保留了与干净版相同的 agent-framework-core 依赖，功能照常工作，窃取器在后台静默运行，开发者完全无感。

如果你怀疑环境里装过恶意包，不要用 pip 卸载（卸载本身会启动一次 Python，触发窃取器）。用 shell 直接清：

这个”先隔离、再清理、最后轮换”的顺序，是处理所有供应链投毒事件的通用流程。

我的做法（手工维护源码于本地路径）虽然看起来”原始”，但它带来了三个确定性优势：

优势 说明
可审计性 每一行代码都在自己手里，随时可以审查
稳定性 不因上游更新而意外改变行为
安全性 不受第三方包被入侵的风险影响

代价是：升级需要手动同步，失去 pip upgrade 的便利。但对于运行在生产环境的核心模块来说，这个代价是值得的。

4. 踩坑记录 — 如果重来，我会怎么做

4.1 预防性措施

  1. 源码备份纳入日常 cron：我的备份脚本确实每天跑，但备份的是运行时文件，没有包含核心源码（因为当时觉得源码在 git repo 里）。教训：重要源码应该在多个位置都有备份，不能只依赖单一存储。

  2. pip install 前先核验：养成 pip show <pkg> 或至少 curl https://pypi.org/pypi/<pkg>/json | jq '.info.summary' 的习惯，确认拿到的是正确的包。

  3. 关键包 pinned 版本：如果必须从 PyPI 安装，用 pip install package==version pin 到已知正确的版本，并在 requirements.txt 里记录。

4.2 恢复过程中的经验

  1. 从运行时代码逆向比从头写更快：我有插件代码作为”消费者侧”的接口定义，这是最权威的 API 规范。从消费侧倒推实现，比凭空设计要准确得多。

  2. JSONL 日志是最好的文档：qgs-history.jsonl 记录了实际运行中的数据结构，包括 score、verdict、issues、suggestions 等字段的真实值，比任何口头描述都可靠。

  3. 保持最小兼容：重建时不需要加入新功能，只需要让现有插件能正常运行。不要在这个过程里”顺便优化”——那是另一个故事的题材。

5. 总结

这次 QGS 源码丢失事件，表面看是一个不幸的技术事故，但深层揭示了一个重要的工程原则：

对于你系统中不可替代的核心组件，拥有源码本身就是最基础的安全措施。

PyPI 上的同名包可能完全不相关（如我们的 qgs 案例），也可能被恶意入侵（如 agent-framework 案例）。把命脉交给别人维护的包，等于把自己系统的可靠性押注在偶发事件不会发生的假设上。

我们的解法是手工重建并用本地路径维护——这听起来不够”现代”，但在生产环境中，可控性永远优于便利性。

如果你也在构建类似的 agent 系统或 AI 基础设施，我建议你对核心模块采取同样的策略：源码自备、版本 pinned、定期备份、必要时能离线审查。

本文提到的重建过程约耗时 2 小时，其中逆向分析 30 分钟、编码 60 分钟、测试调试 30 分钟。重建后的代码已通过 pip show 确认不与任何 PyPI 同名包冲突。
