把一个 740MB 的 git 备份仓库瘦到 6.4MB——历史膨胀与跨洋 push 的治理实录

发表于2026-11-28|更新于2026-11-28|技术实战

一句话摘要：一个每天自动备份配置的 git 仓库，悄悄膨胀到 740MB，.git 里躺着 100MB 的 pack 文件，跨洋 push 还要 10 多分钟。本文记录我用 git-filter-repo 把历史从 740MB 砍到 6.4MB、并借 Cloudflare 网关把 force-push 干到 17 秒的全过程。

1. 缘起

我的服务器上跑着 Hermes Agent，它有个自动备份机制：每天把 AI Agent 的配置、技能、插件、记忆、数据库整个打包，commit 进一个 git 仓库并推送到 GitHub。设计很合理——git clone 到新机器、跑个恢复脚本就能还原整个环境。

直到有一天我发现仓库越来越不对劲。git count-objects -vH 一看：

一个”备份配置”的仓库，.git 里躺了 776MB。更夸张的是，顺着历史翻最大的几个对象：

看清楚了吗？我在 git 仓库里 commit 了 git 的 pack 文件、checkpoint 数据库、48MB 的缓存 JSON。每次备份快照几百 MB，历史一层层叠，就算工作区看着很小，历史里的每个对象都永远占着位置。这就是”工作区瘦了、仓库没瘦”的经典陷阱。

2. 核心方法

2.1 先认清膨胀的三个元凶

  1. 把运行时数据当”配置”备份：checkpoints/store/objects/pack/*.pack、tasks.db、index-cache/*.json 这些是运行时产物，不是配置。每次快照都是几百 MB 的大 commit。
  2. 备份脚本用”整体重建”策略：rm -rf hermes_backup && 重新拷贝，工作区永远只有最新一份——但 git 历史里每个旧版本的对象都永久留存。删除不会让仓库变小。
  3. 跨洋推送慢：服务器不在 GitHub 网络附近，几百 MB 的 pack 每次 push 都要传很久，甚至超时失败。

2.2 用 git-filter-repo 重写历史

直接 rm 文件没用，必须重写历史，把那些大对象从历史里彻底抹掉。工具选 git-filter-repo（比 filter-branch 快一个量级，而且会主动处理 reflog、tag 等边角）：

--refs HEAD -- 50 的意思是：把 HEAD 的历史截断到最近 50 个 commit，再往前的一律作废。重写后 git count-objects 立刻健康：

⚠️ filter-repo 不是 git 自带工具，且它会彻底改写 commit hash、清理 reflog。单人仓库放心用；如果有协作伙伴，重写前一定先通知他们 clone 新的。

2.3 把 rewrite 的历史推上去

历史改写后本地是新的，远端还是旧的，push 会冲突——必须 --force。这一推，跨洋慢的问题就爆出来了。

3. 踩坑记录

3.1 坑一：以为”删了文件”仓库就会瘦

我第一次是想偷懒，git rm 掉那些大 pack 文件再 commit。结果是仓库根本没变小——旧对象还在历史里。只要对象还在可达的历史中，git 就永远不会清它。 这是 90% 的人栽的第一个坑。要瘦身，不是删文件，是改历史。

3.2 坑二：push 太慢 → 想到了”中转”

历史砍小了，但直接 git push -f origin main 仍可能因为跨洋链路慢/不稳定而超时。我的解法是走一层 Cloudflare Gateway 中继：在网关侧配置好 GitHub 的 ssh 转发，本地 git 只往网关 push，网关再转给 GitHub。实测 force-push 一次 17 秒搞定。好处是链路上多了个稳定的 CDN 边缘节点，比直连跨洋稳定太多。

3.3 坑三：push 失败的”云端兜底”思路

如果 push 就是连不上怎么办？我在备份脚本里加了一招 fallback：本地 push 失败时，先把当前 main 推到 backup-push 分支，然后触发一个 GitHub Actions workflow，由云端执行 git push origin HEAD:main --force。相当于让 GitHub 自己完成最后一跳——本地到远端只传增量分支，剩下的在云端内网完成，稳。

4. 总结

  • 备份仓库变大的根因是”把运行时数据当配置 commit + 历史不清理”。git count-objects -vH 和 git rev-list --objects --all | git cat-file --batch-check 是排查膨胀的两把钥匙。
  • 瘦身正确姿势：git-filter-repo 重写历史（截断到 N 个 commit 或按路径过滤），不是 git rm。单人仓库放心用，协作仓库先通知伙伴。
  • 大仓库跨洋 push：走 CDN/网关中继，或做”云端 Actions 兜底 push”，把最慢的最后一跳交给 GitHub 内网。

治理完之后，这个备份仓库从 740MB 降到 6.4MB，推送从 10 多分钟（甚至失败）变成 17 秒，每天自动备份又快又稳。如果你的 CI/备份仓库也在悄悄膨胀，先用 git count-objects -vH 看看它有多少斤两——多半会让你吓一跳。
