我们把 LLM 路由器冷启动从 65 秒干到 1.7 秒——决策缓存三件套实战

发表于2026-11-05|更新于2026-11-14|工程实践

一句话摘要：我们在自己的 LLM 智能路由器（OpenLLM）里实现了一个「决策缓存 + 护栏校验 + 原生执行器」三件套，把 auto/fusion 虚拟模型的二次请求延迟从 65.9s 压到 1.75s（~97% 下降）。这个方案受 HarnessMM（arXiv:2610.32813）启发，但做了三个关键工程决策——其中两个是被生产环境实测打脸后补出来的。文中给出完整指纹设计、缓存失效策略和两个反直觉的坑。

1. 缘起 — 一个”自动选最好的模型”的路由器，自己却成了最慢的一环

我们的 OpenLLM 是一个多租户 LLM 网关，对外暴露 auto 和 fusion 两个虚拟模型。用户不用关心后端到底有多少个 provider 和模型，网关自动帮他们选最好的——这是智能路由的价值。

但有个致命痛点：auto 模型的冷启动要 60 多秒。

为什么这么慢？因为每次请求进来，SmartRouter 都要做这些事：

  1. 从数据库收集全目录候选模型（100+ 个）
  2. 对每个候选跑 bandit 打分（健康度、延迟、价格、能力匹配）
  3. 构建 fallback 链，计算超时
  4. 真正执行请求

这个流程是每请求都跑一遍的。而同一用户、同一会话内的连续请求，路由决策几乎一模一样——都是一样的模型、一样的 provider、一样的 key。我们却每次都重复算一遍，纯属浪费。

问题在于：怎么判断”这次请求跟上次一样，可以复用上次的决策”？

这就是我们复现 HarnessMM 轻量化思路的出发点。

💡 HarnessMM（arXiv:2610.32813）是一篇关于 Agent harness token 效率优化的论文。核心思想：当决策已经”settled”（稳定、可复现），就把它缓存下来，后续只做守卫校验（guard holds）就直接复用，不再重新推理。论文在 Codex + HumanEval 上把 tokens/task 降了 29.54%。

2. 核心方法 — DecisionCache + GuardChecker + NativeExecutor 三件套

我们在 server/services/router.ts 的 route() 入口实现了三个组件，拼成一条快速路径：

2.1 DecisionCache — 指纹要够「颗粒」才能安全复用

缓存的 key 是请求指纹（FNV-1a 32-bit 哈希）。关键在设计指纹包含哪些维度。我们踩的第一个坑就在这（详见第 3 节）：

为什么要有 v=/t=/s= 三个信号？ 因为缓存是”把上次的决策复用给这次的请求”。如果上次决策是针对短文本聊天选的模型，这次来个带图片的 vision 请求，模型不支持视觉——复用就会出错。

这三个信号把指纹按”能力 + 规模”分桶：v=true 和 v=false 的请求永远不会共享缓存。

TTL 5 分钟，500 条 LRU。 只缓存无显式限制的虚拟模型（auto/fusion）。带 provider/model 限制的请求永远走全量打分——因为限制越具体，决策越不可复用。

2.2 GuardChecker — 复用前先体检，任何一个守卫不过就失效

缓存的决策是 5 分钟内算出来的，但 5 分钟内 key 可能冷却、预算可能超、provider 可能下线。所以复用一个缓存决策前，必须先跑一遍守卫校验：

守卫 检查什么 失败动作
key 健康 decision.key.status === "healthy" 删缓存 + 全量打分
冷却中 retry_after_* 设置是否过期 删缓存 + 全量打分
月度预算 估算 tokens 是否超 budget 删缓存 + 全量打分
自定义模型预算 custom/* 的独立预算 删缓存 + 全量打分
provider 注册 adapter 还在 registry 里 删缓存 + 全量打分
能力匹配 这次要 vision，模型支持吗 删缓存 + 全量打分
退休信号 retirement_* 设置 删缓存 + 全量打分

任何守卫失败 → 立即 decisionCache.delete(fingerprint)。这很重要：如果不删，同样的请求会在 TTL 内反复走守卫然后失败，每次都白跑。

2.3 NativeExecutor — 直接执行，不重建 fallback 链

缓存命中且守卫全过后，进入快速执行路径。核心是跳过 bandit 打分和 fallback 链重建，直接拿缓存的 decision 去调 provider：

关键：失败即失效缓存。 如果缓存的决策执行失败，说明这个决策已不再有效（比如 key 被禁用但守卫没检查到），必须删掉并回落到完整打分流程——否则同一条坏决策会在 TTL 内被反复重试。

2.4 实测数据

部署到 Deno Deploy 后的生产验证（https://openllm.yadinae.deno.net 真实请求）：

请求 延迟 路径 备注
冷启动（全量打分） 65.9s full path 首次请求无缓存
第 2 次命中 2.49s native: true _routed_via.native: true
第 3 次命中 1.75s native: true 稳定在 2s 以内

~97% 延迟下降——主要省掉的是打分 + 候选收集的 DB 往返。注意上游推理本身仍占大头，这 1.75s 里路由器自身开销已经降到几毫秒级。

3. 踩坑记录 — 两个被生产环境实测打脸的决策

坑 1：指纹不含能力信号 → vision 请求错配到文本决策

症状：一个带图片的请求被复用到了为纯文本请求选出的决策，模型不支持 vision，直接报错。

根因：最初的指纹只包含 model + roles + max_tokens + temperature。但一个 4 个文本消息的会话和一个 4 个消息（含 1 张图片）的会话，指纹完全一样——因为我们没把消息内容算进去。

修复：补上 v=hasVision / t=hasTools / s=inputSizeBucket 三个能力/规模信号。这样带图请求和纯文本请求永远分属不同缓存桶。

💡 教训：设计请求指纹时，不只要区分「内容不同」，更要区分「能力需求不同」和「输入规模不同」。能力信号决定模型能不能用，规模信号决定 context window 够不够。

坑 2：NativeExecutor 失败不失效 → 同一条坏决策被反复重试

症状：某个缓存决策指向一个刚被禁用的 key，首次执行失败，但后续请求继续命中缓存、继续失败，TTL 5 分钟内反复重试。

根因：executeNative 失败时直接 return，没删缓存。守卫检查是执行前跑的，但 key 可能在两次请求之间刚被禁用——守卫看时是健康的，执行时已经挂了。

修复：失败即 decisionCache.delete(fingerprint) 再回落全量链。这样坏决策最多被重试一次，之后自动重新打分选新路径。

坑 3（架构边界）：进程内缓存 = 冷启动时缓存归零

这个坑来自 Deno Deploy 的 platform 特性：免费版在零流量时缩容到 0，进程内缓存全部丢失。决策缓存依赖实例内存，所以冷启动场景下缓存命中率为 0，首请求必然走全量打分。

这不是缓存实现的 bug，而是 serverless 的固有约束。 缓解方案：

  • 在数据库建 Active Profile（配置级首选链），让首请求也有候选集裁剪（100+ → <10）
  • 用保活请求（keepalive）维持实例常驻

我们后来在 11-04 的「深夜冷启动」事故里踩了更深一版（见后记），核心结论就一句话：

任何依赖「实例内存缓存/状态」的性能优化，在 Serverless 免费版缩容至 0 的场景下都会失效；必须配合「配置级首选链（Active Profile）」或「最小实例数>0」才能保证冷启动稳定。

4. 总结

核心 takeaway：路由决策是高度可复用的——同一会话内连续请求，决策结果几乎一样。与其每次都花 60 秒重算，不如把决策缓存下来，用「指纹 + 守卫」确保安全复用。

  • 指纹要含能力信号（vision/tools/规模），否则复用会错配
  • 守卫校验失败必须删缓存，否则坏决策在 TTL 内反复重试
  • 执行失败必须失效缓存，回落到全量打分
  • 进程内缓存依赖实例常驻，serverless 冷启动场景需配合配置级首选链

架构选择：我们选了进程内 LRU + FNV-1a（零依赖、部署即用），而不是 Redis/KV 全局缓存。代价是 Deno Deploy 多 isolate 间命中率随负载均衡波动（platform 特性非 bug）。收益是零外部依赖、零运维成本、部署即用。
