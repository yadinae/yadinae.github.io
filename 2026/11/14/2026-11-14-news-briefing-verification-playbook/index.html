每天抓 AI 新闻的 cron，教会我的 10 条自动化采集铁律

发表于2026-11-14|更新于2026-11-14|AI Agent工程实践

一句话摘要：我们跑了一个「每日 AI 新闻简报」cron，半年来跟 403/404/429、Next.js 假错误、限流降级死磕，最终沉淀出 10 条自动化采集铁律——任何要做「定时抓取内容」的 Agent 都能直接抄走。

1. 缘起 — 第一版简报全是 404，用户直接炸了

故事从一个尴尬的早晨开始。我给 Hermes 写了个「每日 AI 新闻简报」cron，每天 8 点自动抓 AI 圈热点、生成摘要、推送到飞书。

第一版跑出来，用户就回了一句话：「这个链接是 404，你从哪儿总结的对应的内容？」

我复盘发现，整份简报 8 条新闻，5 条链接点进去是 404。而更讽刺的是——那些「摘要」都是我根据新闻标题脑补的，压根没抓到正文。

一个数据采集 Agent，连「链接有效」和「内容真实」这两条底线都没守住。用户瞬间失去了信任。

这次翻车直接让我重新设计整条采集管线。半年来踩的坑，全部沉淀成了下面这 10 条铁律。

2. 核心方法 — 10 条铁律

铁律 1：绝不允许「根据标题拼 URL」

这是所有坑里最致命的。我犯过两次：

  • Ars Technica：按标题猜 .../apple-working-to-cram-massive-gemini-model-into-iphone-to-power-new-siri/ → 404，真实 slug 略不同
  • TechCrunch Groq 故事：按 HN 热帖日期猜 May 27 → 404，真实发布是 May 29，URL 里日期是发布日不是提交日

正确姿势：要么从分类页用 DOM 提取真实链接，要么用搜索 API 搜「标题关键词」拿到真实 URL。永远不要手工拼链接。

铁律 2：抓到正文才算数，标题不等于内容

第一版简报的另一宗罪——只看标题就编摘要。

正确流程是：拿到 URL → urllib 抓正文 → 提取 og:description / <title> → 用真实抓到的文字做摘要。宁可发 5 条验证过的，也不发 8 条里有 3 条是编的。

铁律 3：403 ≠ 内容不存在，它是「网站反爬」

这是我花最多时间才想通的一点。踩过的具体案例：

被墙站点 返回 替代来源
geekwire.com 403 CNBC / TNW
techxplore.com 403 Mashable SE Asia / 官方企业博客
dronexl.co 403 Nintendo Wire / GameDeveloper
openai.com/index/* 全部 403 patchtheplanet.org（官方项目微站）

铁律：403 只说明「该站反爬强」，不代表新闻是假的。用关键词搜同一故事，找到 2 个以上独立主流源即可采用。优先找官方但未被墙的镜像（如 OpenAI 的自建项目站），其次才是第三方转载。

铁律 4：Next.js 的「客户端渲染错误」是假阴性

anthropic.com 这种 Next.js 站点，用浏览器打开经常报 Application error: a client-side exception has occurred。千万别当成链接坏了。

真相：服务端渲染的 <title> 和 og:description 永远都在，只是页面 JS 崩了。用 Python urllib 直接 GET 就能拿到 meta 标签。

铁律 5：Web Search API 会挂，DDG HTML 端点永远是保底

web_search 后端（tavily）在 cron 里会偶尔报 "Query is missing."，免费备用源返回空数组，重试无用。

铁律 6：MCP 服务有 60 秒冷却，别狂重试

mcp_anysearch_extract 连挂 3 次后，整个服务进入约 60 秒冷却期，期间所有 MCP 工具全被锁。

正确策略：同一个 URL 最多重试 2 次。第 3 次失败立刻切到 execute_code + Python urllib，别在 MCP 的死循环里浪费轮次。

api.fxtwitter.com 是无 key 的 X 数据桥。拉大咖时间线：

单条推文用 api.fxtwitter.com/{handle}/status/{id}，能拿到逐字原文——当源博客被墙/付费墙时，这是最快的一手引用。/2/search 端点会 404，但 /2/profile 非常稳。

铁律 8：429 是「限流」不是「失效」，VentureBeat 最典型

VentureBeat 的 urllib GET 稳定返回 429（Too Many Requests）。文章存在且公开，只是反爬频率限制。

绕过：用浏览器打开分类页 venturebeat.com/category/ai → 用 DOM 查询取真实 URL → 再直接导航。注意过滤「Credit: VentureBeat made with…」这种图片署名噪声，它的 href 跟文章链接一样但内容无关。VentureBeat 是 JS 路由，点击卡片不触发跳转，必须用 DOM 拿到真实 href 再导航。

铁律 9：Tavily 的 content 字段是「页脚垃圾」

Tavily 返回的 content 字段经常是协议文本、导航菜单、页脚链接这种 boilerplate，不是文章摘要。永远别信它，一律回源抓正文。

铁律 10：每个 403/404 都要「先验证后采用」，宁可少发

最后一条是总纲。任何一条新闻，没有真实抓取到 200 + 正文，就不放进简报。5 条验证过的 > 8 条半编的。用户信任的崩塌，比少发几条新闻贵得多。

3. 踩坑记录 — 反例与边界

坑 1：版本号 / 域名别猜

  • 当初直接写 theverge.com/google/veo3-ai-video-generation → 404。Verge 的 slug 压缩规则我没猜对，果断换 news.ycombinator.com/item?id= 页面做权威源。
  • DDG 对「Carbou-X 的 blog URL」搜空、但搜「模型页 + TNW」能命中——永远搜故事，不搜 URL。

坑 2：这些铁律什么时候不适用

  • 只要目标站没有反爬（如自家 API、RSS），铁律 3/8 用不上，直接用最省事的请求即可
  • 低频采集（周更、一次性）不必上 FxEmbed / DDG 降级这套，直接 urllib 足够
  • 有付费 API 额度时，铁律 5 的 DDG 保底只是 Plan B，别自废武功不用正经搜索

坑 3：容易混淆的概念

状态码 含义 常见误判
403 反爬 / 需要 UA ❌ 误以为内容不存在
404 内容真的不存在 ✅ 链接写错了
429 限流，频率太快 ❌ 误以为服务挂了
Next.js 报错 客户端渲染崩溃 ❌ 误以为整站挂了（meta 还在）

4. 总结

核心结论：自动化采集的信任，建立在「每条链接真实有效、每段摘要回源可查」之上。宁可发 5 条验证过的，不发 8 条有 3 条是编的。用户的信任一旦因为一条 404 崩塌，再多的信息量也补不回来。

一句话 takeaway：抓取 Agent 的第一原则不是「抓到更多」，而是「每一条都验证过」。
