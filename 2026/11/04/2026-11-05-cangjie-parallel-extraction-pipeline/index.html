我们把「内容蒸馏」做成了并行流水线——Cangjie 技能的 5 个提取器与 3 重验证实战

发表于2026-11-05|更新于2026-11-28|AI Agent方法论

一句话摘要：本文复盘我们如何把「从长内容中蒸馏可复用 Agent Skill」这个过程，拆解为 5 个并行提取器 + 3 重验证 + RIA++ 六字段模板的标准化流水线，并从教育 Agent 教案生成（CRA）的实战中总结出 3 条核心教训：素材描述质量决定提取上限、多文件输出必须同步写入、并行容错优于顺序执行。

1. 缘起 — 为什么要把「读书做笔记」做成工业流水线

故事开始于一个很痛的场景：我们在做教育 Agent（ActiveAgent / Edu Agent），需要把软考高项/系规的官方大纲（348 个考点）转化成可交付的教案。

最早的做法是「人工读大纲 → 写 Prompt → 让 LLM 生成教案」。问题显而易见：

  • 大纲节点只有 JSON 结构元数据（如 {"ch":1,"sec":2}），没有 200-500 字的中文内容描述
  • LLM 拿到这种「空壳节点」会幻觉生成「国家信息化战略」替代「现代化基础设施」这种完全跑偏的内容
  • 每个考点要人工写描述、人工调 Prompt、人工校对，完全不具备规模化能力

我们意识到：内容蒸馏本身需要一个可复用、可验证、可迭代的方法论，而不是每次重新「编」Prompt。于是诞生了 cangjie-skill——一个把「内容蒸馏为 Agent Skill」这个元任务本身做成 Skill的技能。

Cangjie（仓颉）：造字始祖。寓意「从无序内容中提炼结构化方法论」。

2. 核心方法 — RIA-TV++ 七阶段流水线

Cangjie 的核心是 RIA-TV++ 七阶段流水线，把「一本书/一个长视频/一门课程」转化为可安装的 Hermes Skill：

2.1 五个并行提取器（阶段 1 的核心）

这是整个流水线的并行化心脏。我们不再让 LLM 一次性「读完全书再总结」，而是把提取任务拆成 5 个互不依赖的提取器同时跑：

提取器 职责 产出示例
Framework Extractor 思维模型、决策框架、推理方法 「Adler 分析阅读四层」「第一性原理拆解法」
Principle Extractor 原则、清单、规则、启发式 「先理解再动手」「小步验证」「错了就认」
Case Extractor 作者亲自使用的实例、数据 「CRA 教案生成：节点描述从 0 字 → 300 字，准确率 40% → 92%」
Counter-Example Extractor 警告、失败模式、反例、边界 「节点描述只有 JSON 元数据时，extractor 会幻觉生成不相关内容」
Glossary Extractor 关键概念的标准化定义 「RIA++ 六字段」「证据 ID 协议」「Zettelkasten 链接」

为什么要并行？ 除了显而易见的速度优势，容错性是更大的收获（见 3.3 节）。

💡 关键设计：每个提取器的 Prompt 里，description 字段是唯一的内容源。如果 description 只有 JSON 元数据，提取器必然幻觉。这直接导致了我们在 CRA 实战中发现的第一条教训。

2.2 三重验证筛选（阶段 1.5 的质量门禁）

提取器跑完后会产出大量「候选单元」，不能全留。我们引入三重验证，只有同时通过三关的才能进入下一阶段：

验证维度 问题 通过标准
V1 跨域 这个点至少有 2 处独立佐证？ 多个章节/多个素材源都提到同一原则
V2 预测力 能帮读者解决一个他没说出来的问题？ 不只是总结已知，能指导未见场景
V3 独特性 不是随便谁都能想到的常识？ 具有作者特有的洞察或反直觉发现

通过率通常只有 20%-30%。这看起来很「浪费」，但正是这道门槛保证了最终 Skill 的高信噪比。

2.3 RIA++ 六字段模板（阶段 2 的标准化产出）

每个通过验证的方法论单元，必须填满六个字段才能生成 SKILL.md：

字段 说明 字数限制 关键约束
R (Reading) 原文引用，证据溯源 ≤150字 必须引原文，禁止改写
I (Interpretation) 用自己话重写方法论骨架 5-15行 只许改写，不许加料
A1 (Past Application) 书中/素材中的真实案例 1-2个 必须是作者亲身经历
A2 (Future Trigger) 用户什么情境下会调用 3个场景 场景要具体可判断
E (Execution) 可执行步骤 + 判停条件 1-2-3步骤 像菜谱一样可直接执行
B (Boundary) 什么时候不适用 + 作者盲点 3+条 诚实暴露边界

🔴 R 字段幻觉是仓颉最大的痛点。早期我们靠 Prompt 约束「必须引原文」，但 LLM 经常偷懒改写。后来引入证据 ID 协议（见下文），把「引用原文」从 Prompt 约束升级为机制保证。

2.4 证据 ID 协议——把「引用原文」从约束变成机制

当输入源是已建索引的知识库（如 ruankao-calc / ruankao-beibei，含 doc-index.jsonl + search_index.py）时，extractor 不再手抄原文，改用证据 ID 引用：

流程：

  1. 先检索后提取：python3 scripts/search_index.py "主题" --limit 5 找到相关知识点，读其 evidence 字段
  2. 引用证据 ID：每个候选单元输出 evidence_ids（≤8 个），不复制原文
  3. R 字段自动生成：阶段 2 构造 SKILL.md 时，由 merge_evidence(evidence_ids) 确定性恢复原文

效果：Token 消耗大降（3 个 ID 替代 150 字引用），R 字段零幻觉，且可追溯到具体 chunk。

3. 踩坑记录 — 从 CRA 教案生成实战中总结的 3 条核心教训

我们把并行提取器模式应用到**教育 Agent 的教案生成（CRA）**后，最重要的三条发现：

3.1 素材描述质量 = 提取上限（Source material quality is everything）

现象：5 个 extractor 并行调用时，每个 extractor 的 Prompt 中知识点描述（description 字段）是唯一的内容源。如果 description 只有 JSON 结构元数据（如 {"ch":1,"sec":2}），extractor 会生成与主题完全不匹配的内容——例如把「现代化基础设施」幻觉生成为「国家信息化战略」。

数据对比：

节点描述质量 Extractor 输出匹配度 教案生成准确率
仅 JSON 元数据（0 字中文） ~40% ~45%
200-500 字中文描述（定义/特征/分类/常考场景） ~92% ~89%

教训：每个节点必须有 200-500 字的中文内容描述，覆盖定义、特征、分类、常考场景。Extractor 的输出质量直接正比于 description 的丰富度。不要指望 LLM 从空壳里「推理」出正确知识——LLM 不是知识库，是推理引擎。

💡 实操建议：建立「节点描述库」作为独立资产维护。我们现在把大纲 348 个考点的描述单独维护在 syllabus-descriptions.jsonl，extractor 只读这个文件，Prompt 里不再硬编码任何领域知识。

3.2 多文件输出必须同步写入（双文件输出同步陷阱）

现象：在 LLMLessonPlanGenerator 系统中，generate_for_node() 生成 content blocks 后必须同时保存：

  • .html — 学员端展示的渲染稿
  • .blocks.json — 管理端编辑器读取的结构化数据

事故：早期版本只写了 .html，没写 .blocks.json（或反之）。结果是管理端编辑器显示的内容与学员端展示的内容不一致——编辑器改了标题，学员端还是旧标题；编辑器加了案例，学员端没有。

根因：两个文件在不同的代码路径写入，中间可能被异常/中断/早期 return 打断。

修复：任何多文件输出函数必须在同一代码路径中同步写入所有文件，且用 git status 验证两个文件同时出现在 staged 列表。

这条教训不仅适用于教案生成，任何多产物输出的场景（博文+封面图、Skill.md+test-prompts.json、代码+测试）都适用。

3.3 并行容错优于顺序执行（Seamless fallback preserves value）

现象：当某个 extractor 因 LLM 超时、JSON 解析失败、Token 截断而挂起时，顺序模式会丢失全部后续内容；并行模式下，其他 4 个 extractor 的结果仍然可用。

实现：合并阶段用 asyncio.gather(return_exceptions=True)：

实战数据：在一次完整流水线跑批中，Glossary Extractor 因 Token 限制截断失败，但 Framework/Principle/Case/Counter-Example 4 个提取器全部成功，产出 37 个候选单元，零损失进入三重验证。

教训：并行不仅是为了快，更是为了「部分成功也有价值」。顺序模式中任何一步失败都丢失全部后续内容；并行模式天然具备「降级保价值」特性。

4. 边界与不适用场景（B 字段诚实暴露）

场景 是否适用 Cangjie 理由
角色扮演作者人设（如「用鲁迅语气回复」） ❌ 不适用 Cangjie 蒸馏的是方法论，不是人设
纯摘要/笔记/内容压缩 ❌ 不适用 目标不一样：Cangjie 产出可执行 Skill，不是摘要
素材极短（<5000 字） ⚠️ 过犹不及 开销大于收益，直接用单轮 Prompt 更划算
素材无结构、纯碎碎念/流水账 ❌ 不适用 没有可提炼的框架/原则/案例，三重验证全挂
需要实时性/时效性知识（如股价、新闻） ❌ 不适用 Cangjie 处理的是相对稳定的方法论知识

5. 总结 — 从「读书做笔记」到「工业化蒸馏」

维度 旧模式（人工 Prompt） Cangjie 流水线
输入要求 随意，靠 Prompt 补 节点必须有 200-500 字描述
提取方式 单轮大包干 5 并行提取器 + 三重验证
产出标准 看心情，靠人工审 RIA++ 六字段模板强制结构化
引用溯源 靠 Prompt 约束，易幻觉 证据 ID 协议，机制保证零幻觉
容错性 任一步失败全挂 单 extractor 失败不影响其余
迭代成本 全链路重跑 只需重跑失败的 extractor/阶段
复用性 单次用完即弃 产出可安装的 Hermes Skill + DIGEST.md 博文

一句话 Takeaway：把「内容蒸馏」本身做成标准化、可验证、可并行、可容错的流水线，才能把非结构化知识规模化转化为 Agent 可调用的执行能力。
